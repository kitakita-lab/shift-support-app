## 1. 目的と範囲

ワークショップ案件を **会場 × 期間 × 実施コンテンツ** の単位で持ち、次の3つを1か所で計画する。

1. **スタッフ配置** — スタッフリストから人が選んで配置する（自動割当てはしない）
2. **収支試算** — 人件費・材料費・会場費・備品費まで含めた案件ごとの収支
3. **ブースレイアウト** — 会場雛形の上に定型パーツを置き、配置図を PDF で出す。パーツ個数は試算と連動

共通原則:
- **UI は表計算に近い見た目**（グリッド線・行番号・常時編集セル・下部のシートタブ）
- **入力チェックは「禁止せず、警告して選ばせる」**（3.5 参照）

## 2. データモデル

単位: 金額＝円、長さ＝cm、時刻＝`HH:MM`、日付＝`YYYY-MM-DD`。定義は `src/types.ts`。

```
Staff ──┐                        Venue ─── template: Layout（周辺環境のみ）
        │ staffId                  │ venueId
        ▼                          ▼
   Assignment ◀── Project ──▶ ProjectContent ──▶ Content ── Material[]
                     │
                     └── layout: Layout ── env: EnvElement[]   （周辺環境。雛形のコピー）
                                        ├─ items: PlacedItem[] ──▶ PartType
                                        ├─ groups: LayoutGroup[]（L字など）◀── Composite（組み合わせの定義）
                                        └─ version / issued[] / caption / notes
```

### 2.1 マスタ

| 型 | フィールド | 説明 |
|---|---|---|
| `Staff` | name, hourlyRate, transportPerDay, memo | 時給と1勤務日あたり交通費 |
| `Content` | name, price, materials[], memo | 実施コンテンツ。price は参加費（無料なら 0） |
| `Material` | name, unitCost, qtyPerUnit | コンテンツ1個に使う材料の単価と使用数 |
| `PartType` | name, shortName, category, widthCm, depthCm, numbered, unitCost, costUnit, stockQty, seatRole | サイズ固定の定型パーツ。category = table / chair / banner / pop / display / partition / other。`seatRole`（椅子のみ）= work（制作席）/ other（その他）。未設定は制作席として読む |
| `Composite` | name, members[{partTypeId, dx, dy, rot}] | 複数台の組み合わせ（L字など）の定義 |
| `Venue` | name, feeFixed, feePerDay, feeRatePct, memo, template, reportNames | 会場費の既定値と、レイアウト雛形。`reportNames`（任意）は、日報での会場名の別の書き方（6.2） |

### 2.2 案件

| 型 | フィールド | 説明 |
|---|---|---|
| `Project` | name, venueId, startDate, endDate, openTime, closeTime, status, memo | 基本情報。status = 計画中 / 確定 / 実施済 / 中止 |
| | contents[], assignments[], otherCosts[] | 実施コンテンツ、スタッフ配置、その他費用 |
| | fixedRevenue, venueFeeFixed, venueFeePerDay, venueFeeRatePct | 固定売上と会場費（会場の既定値をコピーして案件ごとに調整） |
| | layout, updatedAt | ブースレイアウト、最終更新時刻（端末の時計。参考情報で、同期の判定には使わない） |
| | jcos, actualsManual（任意。Version 4） | JCOS 案件の収支の条件（請求・支払いの単価、追加の請求、日ごとの設定）と、手入力の実績個数。`jcos.enabled` が true の案件だけ、JCOS の収支計算を使う（6.1） |
| | reportSource, reportSync, reportClaims（任意。Version 4） | 日報の場所、最後に成功した同期の結果（日別の実績ほか）、会期が重なる案件があるときに「この案件の実績にする」と決めた日（6.2） |
| `ProjectContent` | contentId, plannedCount, priceOverride, sparePct, maxTurns | 予定個数（期間合計）、参加費の上書き、材料の予備率、上限回転数（制作席 1 席が 1 日に受けられる回数。任意） |
| `Assignment` | staffId, date, startTime, endTime, breakMinutes, rateOverride, transportOverride, memo | 1人×1日の配置。時給・交通費は案件別に上書き可（null ならマスタ値） |

### 2.3 レイアウト

| 型 | フィールド | 説明 |
|---|---|---|
| `Layout` | width, height | 図面全体のサイズ（cm） |
| | env[] | 周辺環境。配列の前にあるものほど奥に描く |
| | items[], groups[] | 配置済みパーツと、組み合わせ配置のグループ |
| | version, issued[] | 現在の版数と、PDF 出力の履歴（版・日付・出力したときの図の内容の指紋 `fp`） |
| | caption, notes | タイトル下の一行注記、未確認事項（1行1項目） |
| `EnvElement` | kind, x, y, w, h, label, sublabel, tone, dir | kind = booth（会場区画）/ passage（通路）/ shop（周辺店舗）/ wall（壁・扉）/ entrance（入口：帯＋矢印＋名前）/ stairs / text |
| `PlacedItem` | partTypeId, x, y, rot(0/90), groupId, label | 左上座標。groupId が同じものは一緒に動く |

設計上の決めごと:
- **雛形はコピーして使う**。案件作成時に会場の `template.env` を案件へ複写する。案件側で周辺環境を直しても雛形は変わらない（「会場雛形として保存」で書き戻せる）。
- **番号は保存しない**。`buildLabels()` が毎回導出する：グループは作成順に ①②…、グループ内のテーブルは `①-1`、グループ外は `表示名＋連番`（例: 商談席1）。増減しても常に連番が保たれる。個別に `label` を入力すればそれが優先で、**その台は連番を使わない**（①-1・受付・①-2。グループ名の副題「横◯台＋縦◯台」は実際の台数のまま）。
- **パーツ個数も保存しない**。`items` を数えるだけ（`countParts()`）。レイアウトと試算が食い違うことがない。

### 2.4 データの置き場所（2 つ。自動では混ざらない）

| 置き場所 | 保存先 | 使える条件 | 入るもの |
|---|---|---|---|
| **この端末だけのデータ** | ブラウザ内（localStorage `kkl_workshop_v1`。V1 から同じキー） | いつでも（未ログイン・Firebase 未設定でも） | 自分で作ったもの。**サンプルの読み込み・バックアップからの復元は、必ずこちらに入る** |
| **共有データ** | Firestore（`teams/{チーム}/…`）。Firestore が正で、端末には「もう 1 つのコピー」を持たない | ログイン中（メンバー制の適用後は、名簿にある人だけ） | チームで共有する案件・マスタ |

- 画面は、いま選んでいる置き場所のデータだけを表示・編集する。どちらを見ているかは、画面上部の色つきの帯（共有＝青／この端末だけ＝黄）に常に出る。
- 置き場所をまたぐのは、案件一覧の **「共有へコピー」／「端末へコピー」** だけ（1 件ずつ・確認つき）。案件が使っている会場・コンテンツ・スタッフ・パーツも、コピー先に無ければ一緒に足す。**コピー先に同じものがあれば上書きしない**（内容が違うものは、その旨を表示する）。コピー元は変わらない。
  - 「共有へコピー」は、共有側に「まだ無い」と確かめることと、作ることを、**1 つのトランザクション**で行う（確かめたあとで、ほかの人が同じものを作っていても、上書きしない）。
    サーバーにつながっていなければ、その場で失敗する（端末内の送信待ちには残らない＝あとから勝手に作られない）。この端末の送信待ちに変更が残っている間も行わない（2.5 の 6）。
    結果は、作り終えてから「お知らせ」に出る（できなかったときは、その理由）。
- 共有データを丸ごと置き換える操作は無い（V2 までの「サンプル読込・復元で共有データが置き換わる」経路を無くした）。
- **名簿から外された端末に残る「控え」は、完全なバックアップではない**（設計上の制約）。共有を使えなくなった時点で送信前だった案件は、
  案件の中身だけを「この端末だけのデータ」に残す。会場・コンテンツ・スタッフ・自作パーツなどの共有マスタは、権限を失った端末には新たに保存しない
  （PR #86 の Codex レビュー 3 回目の指摘に対する、オーナーの仕様判断。技術的に解決したのではなく、現状維持を選んだもの）。
  そのため、控えの案件は参照先が欠け、金額や図が元どおりに表示されないことがある。画面のお知らせにも、その旨を表示する。
- 「この端末だけのデータ」は変更のたびにすぐ保存する（入力直後に閉じても消えない）。

### 2.5 共有データの同期（`src/store/`）

**Firestore 上の置き場所**（アプリが使う場所は `src/store/paths.ts` だけが組み立てる。一覧は `collections.json`）

| 場所（`teams/{チーム}/` の下） | 内容 |
|---|---|
| `wsStaff`・`wsVenues`・`wsContents`・`wsPartTypes`・`wsComposites` / `{id}` | マスタ。**1 件＝1 ドキュメント**（中身の項目 ＋ 管理用の `order` 並び順・`rev` 書き込みの印・`updatedBy` 最後に書いた人） |
| `wsProjects/{id}` | 案件。1 件＝1 ドキュメント（同上） |
| `wsMeta/state` | 形式の版（`formatVersion: 1`）、使える状態かどうか（`status`）、移行の記録（件数表） |
| `wsBackups/{バックアップ名}__…` | 移行前バックアップ（以前の形式のドキュメントの写し） |
| `members/{メールアドレス（小文字）}` | メンバー名簿（`role: owner / member`） |
| `wsRulesProbe/probe` | 何も置かない。メンバー制のルールでは誰にも許可しない場所。ここを読めたら「ルールが名簿で制限していない」と分かる |
| `workshopData`・`workshopProjects` | V1・V2 の形式。**読むだけ**（移行元）。書き込む処理は無い |
| `appData`・`presence`・`editingStates`・`activityLogs` | 旧アプリ（シフト作成サポート）のデータ。このアプリは読み書きしない |

チーム名は既定で `intention-dev`（環境変数 `VITE_TEAM_ID` で変えられる。プレビューと本番で置き場所を分けたい場合に使う。**現在は設定していない**）。

**同期の規則**（`sharedSession.ts`）

1. **Firestore が正**。画面の内容 ＝ Firestore から届いた内容 ＋ まだ届いた内容に反映されていない自分の変更。
2. **書き込みは 3 種類**: 新しく作る＝「作成」／既にあるものを変える＝「更新」（**自分が変えた最上位の項目だけ**を、入力が止まって 0.7 秒後に送る）／削除。
   - 既にあるものへの変更は必ず「更新」なので、**ほかの端末で削除されたものが復活しない**（Firestore が拒否する）。
   - 送るのは変えた項目だけなので、**別々の項目・別々の行の同時編集は互いを上書きしない**（例: 一方がスタッフ配置、他方がレイアウト）。
3. **入力中の内容は、届いた古い内容で巻き戻さない**（自分が変えた項目だけ手元を優先。触っていない項目は、ほかの人の変更がそのまま見える）。
4. **同じ項目を同時に変えた場合は、後からサーバーに届いたほうが残る**（後勝ち。端末の時計は使わない）。単位は最上位の項目。→ 残るリスクは 2.8。
5. **ログインしただけでは、Firestore に何も書き込まない**。初期設定（「共有データを使い始める」）と移行は、画面のボタンを押したときだけ行う。
6. **送れなかった変更は黙って捨てない**（下の「未送信の変更」「書き込みが拒否されたとき」）。

**未送信の変更**

- 圏外のあいだの変更は、Firestore の端末内キャッシュ（IndexedDB）に送信待ちとして残り、つながると**そのまま**送られる（後勝ち。2.8 の 4）。画面を閉じても残る。ヘッダーに「オフライン（未送信 n 件）」と出る。
- 入力してから送るまでの 0.7 秒のあいだに画面を閉じても消えないよう、変更のたびに **控え**（localStorage `kkl_outbox_v2:{チーム}:{アカウント}:{画面の印}:{場所}/{ID}`）へすぐ書く。届いたと確認できたら消す。
  - 控えは **「画面（タブ）× ドキュメント」ごとに 1 つ**。開いているほかの画面の控えを上書きしたり消したりしない（同じ案件を 2 つの画面で編集しても、互いの控えを壊さない）。
  - 控えを保存できない（ブラウザの保存領域がいっぱい）ときは、1 回だけ知らせる。送信は続ける。
- **前回の残り**（控えを書いた画面がもう無いもの。同じ画面でログインし直した場合の、前のログインの分を含む）は、開いている画面が引き取る。
  引き取るのは、共有データを表示した直後と、その後 12 秒ごと・画面に戻ったとき・接続が戻ったとき。同時に 1 つの画面だけが行う（二重に引き取らない）。
  1. 引き取った変更は、**すぐ画面に重ねて表示し、未送信として数える**（圏外でも）。その上に新しい変更を重ねてよい（控えは 1 件にまとめ直す）。
  2. **共有側のいまの状態を確かめるまでは、そのドキュメントへの変更を送らない**（古い内容で、ほかの人の新しい変更を巻き戻さないため）。つながったら、サーバーから読んで決める
     （「読んで決める」ことと「送る」ことは、切り離さない。下の 6）:

  | 共有側の状態 | 扱い |
  |---|---|
  | 既に届いていた（内容が同じ） | 何もしない |
  | 誰も触っていない（共有側の印が、**引き取った残り自身の**「変更を始めたときの印」か「その残りが送った印」のまま） | 送る（必ず「更新」として）。その上に重ねた今回の変更は、続けて、ふつうの変更として送る |
  | ほかの人が変更していた | **上書きしない**。表示して、案件は「この端末だけのデータ」に「（控え）」として残す（その上に重ねた今回の変更も、同じ控えに入る） |
  | 削除されていた・保存されていなかった | 復活させない（作り直さない）。表示して、案件は控えを残す |
  | 前回の「削除」が届いていなかった | 送り直さない。「削除が反映されていませんでした」と表示する |
  | 送ろうとしたが、書き込みが受け付けられなかった（権限が無い・1 件の大きさの上限超え、など。やり直しても通らないもの） | 繰り返さない。理由を表示して、案件は控えを残す（その上に重ねた今回の変更も、同じ控えに入る）。権限が無い場合は、登録状況を確かめ直す |

  3. いまのログインでこの画面が書いた控え（編集・送信中のもの）は、前回の残りとして扱わない。開いているほかの画面の控えも引き取らない。
  4. 「誰も触っていない」の判定に使うのは、**引き取った残り自身の履歴だけ**。その上に重ねた今回の編集の基準（＝いまの共有側の印）や、この画面の送信の印は使わない
     （使うと、ほかの人が変更したあとの印で、古い残りまで「安全」と判定してしまう）。基準の違う複数の残りをまとめて引き取ったときは、すべての残りに共通する印だけで判定する。
     まとめた控えを残したまま画面がまた閉じられた場合も、次に引き取る画面は同じ規則で判定する（控えに、判定に使う印の一覧を残す）。
  5. 一連の変更のうち、**届いたと確認できた項目は、控えの「変えた項目」から外す**。残りを後で送るときに、確認済みの項目まで古い値で送り直さない（その間にほかの人がその項目を変えていても、巻き戻さない）。
  6. **「確かめる」ことと「送る」ことは、1 つのトランザクションで行う**（`remote.ts` の `recoverDoc`。判定は `sharedLogic.ts` の `judgeRecovery`）。
     確かめたあと、書き込みが届くまでの間にほかの人が保存した場合は、トランザクションがやり直しになり、もう一度確かめる（古い内容で上書きしない）。
     サーバーにつながっていなければ、その場で失敗する。**端末内の送信待ちには入れない**（確かめた結果が古くなってから送られることが無い）。次の機会に、確かめ直すところからやり直す
     （やり直すのは、通信できない・時間切れ・ほかの人の保存と重なった、の場合だけ。書き込みが受け付けられなかった場合は、上の表のとおり、繰り返さない）。
     この書き込みは、ふつうの変更と違って、端末内の送信待ちの列を通らない。そのため、前後で次の 2 つを守る:
     - **先に、送信待ちが空になるのを待つ**（空にならなければ、今回は何もせず、次の機会を待つ）。
       送信待ちに、同じものへの古い書き込み（前回の画面が先に送ったもの、など）が残っていると、それがあとから届いて、順番が入れ替わるため。
     - **片付ける前に、共有側のいまの内容を読み直す**（読み直せなければ、片付けずに次の機会を待つ。その間も、画面には重ねて出し続ける）。
       トランザクションで書いた内容は、購読（画面の元になる内容）には少し遅れて届く。届く前に重ねて表示するのをやめたり、その上の変更を送ったりすると、画面が一時的に古い内容に戻るため。
     書き終えたことは、控えにも記録する（片付ける前に画面がまた閉じられても、次に引き取る画面が、重ねてあった変更を「誰も触っていない」と正しく判定できる）。
- **12 時間以上、送信待ちのままだった変更が送信されたとき**（同じ画面を開いたままの場合と、開き直した場合の両方）は、「お知らせ」に対象と経過時間を表示する。
  これは **防止ではなく通知**（送信待ちは、つながった時点でそのまま送られる。2.8 の 4）。
- ログアウトするときに未送信の変更があれば確認を出し、OK なら破棄する（別のアカウントの名前で送られることはない）。

**書き込みが拒否されたとき**（画面上部の「お知らせ」に、閉じるまで表示）

| 原因 | 表示 | データ |
|---|---|---|
| ほかの端末で削除されていた | 「…は、ほかの端末で削除されていたため、変更を共有データに反映できませんでした」 | 復活しない。案件は、編集していた内容を「この端末だけのデータ」に「案件名（控え）」として残す |
| 権限がない（名簿から外された・ルールが変わった） | 「…書き込む権限がないため、反映されませんでした」 | 画面は共有の内容に戻る。案件は控えを残す。登録状況を確かめ直す |
| その他（1 件 1MB の上限超えなど） | 「…保存できませんでした（理由）」 | 同上 |

**共有データの状態**（共有データを選んでいて使えないときは、理由と次の操作を案内する）

| 状態 | 意味 | 画面 |
|---|---|---|
| 確認中 | 登録状況と形式を確認している | 「共有データを確認しています…」 |
| 未登録 | このアカウントは名簿に無い（メールアドレス未確認を含む） | 案内のみ。共有データは読み込まない・端末にも残さない |
| 準備前 | まだ誰も使い始めていない | 管理者: 「共有データを使い始める」ボタン／メンバー: 管理者待ち（用意されると自動で切り替わる） |
| 移行が必要 | 以前の形式のデータがある | 管理者: 「新しい形式へ移行する」「移行せず、空の状態から始める」／メンバー: 管理者待ち |
| 更新が必要 | 共有データが、このアプリより新しい形式 | 表示と編集を止める（古い版で書き換えない） |
| 確認できない | 接続できず、前回の確認結果も無い | 「もう一度確認する」 |
| 使える | — | ヘッダー: 保存済み／同期中…／オフライン（未送信 n 件）／送信待ち（未送信 n 件） |

圏外で開いた場合は、前回の確認結果と端末内キャッシュで表示する（つながったら確かめ直す）。

**アカウントの切り替えと、端末内キャッシュ**

- ログアウト・別アカウントでのログイン・名簿から外されたことが分かった時点で、端末内キャッシュ（閲覧用の控えと送信待ち）を消して接続を作り直す。前のアカウントの共有データは、画面にも端末内にも残さない。
- 端末内キャッシュは、同じブラウザで開いている画面（タブ）すべてが共有している。「いま誰のキャッシュか」を localStorage の印（`kkl_shared_cache_v2`）で覚えておく。
  - 消すのは、別のアカウントでログインしたとき、または、ログアウトしたとき（そのキャッシュを使っていた画面か、ほかに開いている画面が無い場合）。印の確認と消去は、画面の間で 1 つずつ行う。
  - **1 つの画面がキャッシュを消すと、ほかの画面の Firestore への接続は使えなくなる**。消し終えたらほかの画面へ知らせ（BroadcastChannel）、知らされた画面は読み込み直す（送信前の変更は控えに残っているので、読み込み直したあとに引き取る）。
  - 消せなかった場合（時間切れなど）は、その画面は端末内キャッシュを使わずに動かし、印は残して、次に開いたときにもう一度消す。
  - 共有データを 1 度も受け取っていないキャッシュ（登録されていないアカウントでログインしただけ、など）は消さない。消すものが無く、消すたびにほかの画面が読み込み直されるため（印に「受け取り始めたか」を記録している）。
- 名簿から外されたことが分かったときは、送信前だった変更を手放す。案件の変更は「この端末だけのデータ」に控えとして残し、残せないもの（マスタの変更・削除）は件数を表示する。

### 2.6 メンバー制（`firestore.v3.rules`・「メンバー」タブ）

- **ルール案**（`firestore.v3.rules`。未デプロイ。`firebase.json` が指す `firestore.rules` は変えていない）:
  - 名簿（`members/{メールアドレス（小文字）}`）にある、メールアドレス確認済みの Google アカウントだけが、そのチームのデータを読み書きできる。
    **Google でログインしたアカウントに限る**（このアプリのログイン方法は Google だけ。メールとパスワードなど、ほかの方法で作られたアカウントは、メールが確認済みで名簿にあっても通さない）。
  - 名簿の変更、形式の情報（`wsMeta`）・バックアップ（`wsBackups`）の作成と更新は管理者（`owner`）だけ。バックアップと形式の情報は誰も削除できない。
  - 形式の情報の「移行済み・使える状態」の印（`status: done`）は、**付いたあとは外せない**（未完了・失敗への書き換えを拒否する）。
  - 以前の形式（`workshopData`・`workshopProjects`）は読むだけ。アプリが使う場所だけを名前で許可し、それ以外・2 階層より深い場所はすべて拒否。
  - 旧アプリ（シフト作成サポート）のデータも、名簿の人だけが読み書きできるようになる。
- **アプリは、現在のルールでもメンバー制のルールでも動く**。ログイン時に「自分の登録状況」と「ルールが名簿で制限しているか」を確かめる。
  制限していない（現在のルール）あいだは、帯に「⚠ メンバー制 未適用」と出る（＝ログインできる人は誰でも読み書きできる状態）。
- **「メンバー」タブ**（管理者。未適用のあいだは準備のためログイン中の人に表示）: 追加・役割の変更・削除。メールアドレスは小文字にそろえて登録する。
  - 管理者が 1 人もいなくなる変更は止める。人数は、**実際に照合に使われる登録**（キーが小文字のメールアドレスのもの）だけを数える。
    そうでない登録（コンソールから手で作った大文字まじりのものなど）は「⚠ 無効な登録」と表示する。
    - この確認は、**画面が表示している一覧ではなく、共有側のいまの名簿**で行う。変更の直前に名簿を読み直し、さらに書き込みと同じトランザクションの中で
      「ほかの管理者が、いまも管理者であること」を読んで確かめてから書く（読んだ登録が書き込みまでに変わると、やり直しになる）。
      2 人の管理者が、古い一覧のまま、あるいはまったく同時に、自分を外そうとしても、後から届いたほうは止まる。
    - **ルール案そのものは「最後の管理者」を守っていない**（ルールは名簿の人数を数えられない）。このアプリの操作では止まるが、Firebase コンソールや、
      別の作りのクライアントからは、管理者を 0 人にできる。ルールでも守るには、管理者の人数を持つドキュメントを足す必要がある（作業ログの「人による判断が必要な項目」）。
  - 自分自身を管理者からメンバーに下げるとき・自分を名簿から外すときは、確認を出す。
  - 名簿が空（有効な管理者がいない）のときは「自分を最初の管理者として登録する」が出る。
  - 名簿の変更は、つながっていなければ**その場で失敗する**（送信待ちに残らない。「失敗」と表示したあとで、後から適用されることはない）。

**実環境への適用手順（未実施。ご指示をいただいてから）**

1. **事前**: 最初の管理者にする Google アカウントを決める。旧アプリ（シフト作成サポート）を使う人も名簿に入れる必要がある（名簿に無い人は旧アプリのデータも読めなくなる）。
   念のため、Firebase コンソールで Firestore のエクスポート（またはアプリの「バックアップを保存」）を取る。
2. **最初の管理者を登録する**（どちらか）
   - A. Firebase コンソールで `teams/intention-dev/members/{メールアドレス（小文字）}` を作る。項目は `role`（文字列）＝ `owner`、`addedAt`（数値）、`addedBy`（文字列）。
   - B. Version 3 のアプリにそのアカウントでログインし、「メンバー」タブ →「自分を最初の管理者として登録する」。
     （現在のルールのあいだは誰でも名簿を書けるので、登録からルールの切り替えまでを続けて行う。）
3. **ルールを切り替える**: `firestore.v3.rules` の内容を `firestore.rules` に反映してデプロイする（`firebase deploy --only firestore:rules`）。
   切り替える直前に、名簿（「メンバー」タブ、または Firebase コンソール）を見て、次の 2 点を確かめる。
   - 管理者が 1 人以上いること（いないと、切り替え後に誰も名簿を変えられない）。
   - **見覚えのない登録が無いこと**（現在のルールのあいだは、ログインできる人なら誰でも名簿を書ける。知らない人が自分を管理者として登録していないかを見る）。
4. **確認**: 管理者でログインし、「メンバー」タブが「適用中」になっていること。名簿に無いアカウントでは「登録されていません」と出ること。
5. **残りのメンバーを登録**（アプリの「メンバー」タブ）。共有データの初期設定または移行（2.7）は、管理者が行う。
6. **戻し方**: 以前の `firestore.rules` をデプロイし直せば、元の状態（ログインしていれば誰でも可）に戻る。名簿のデータは残る。

**管理者が誰もいなくなった場合の復旧**: 上の 2-A の方法で、Firebase コンソールから管理者を登録し直す（コンソールはルールの制限を受けない）。

### 2.7 以前の形式（V1・V2）からの移行と、古いアプリとの関係

V2 までは、マスタを種別ごとに 1 かたまりで保存していた（`workshopData/{種別}`）。このため、後から保存した端末がかたまりごと上書きし、ほかの人の追加が消えた。Version 3 は 1 件＝1 ドキュメントの新しい場所（`ws…`）を使う。

**移行**（管理者がボタンを押したときだけ。以前の形式のデータは読むだけで、書き換えも削除もしない）

1. 開始を記録する（`wsMeta/state` を `running` に。やり直しのときは同じバックアップ名を使う）。
2. **移行前バックアップ**を取る: 以前の形式のドキュメントの写しを `wsBackups` へ。同じ内容の JSON ファイルを、操作している端末にも保存する（このアプリの「バックアップから復元」で読める形）。
3. 新しい形式で書く。ドキュメント名は元の ID（**やり直しても同じ場所に上書きされるだけで、増えない**）。
4. サーバーから読み直して、**件数と 1 件ずつの内容**を移行元と照合する。
5. 一致して初めて `status: done`（＝移行済みの印）を付ける。**印が付くまで、どの端末も移行先を使わない**。

- 2〜5 の書き込みは、どれも **「いまも自分の試行が有効か」を確かめてから書く**（Firestore のトランザクション。`wsMeta/state` が `running` で、試行番号が自分のものであるときだけ書く）。
  - ほかの端末が移行をやり直した・完了させたあとは、**古い試行は 1 件も書けない**（完了後に編集されたデータを、移行前の内容で上書きしない。完了の印を「失敗」に書き換えない）。古い試行の端末には「この端末での移行は中止しました」と表示する。
  - つながっていない間の書き込みは、その場で失敗する（送信待ちに残らないので、後日つながったときに古い書き込みが送られることがない）。
  - 1 回に書くのは 8 件まで（メンバー制のルールは、書き込み 1 件ごとに名簿を見る。ルールが 1 回のまとめ書きで「ほかのドキュメントを見てよい回数」の上限＝20 回に、最悪の場合でも触れない件数にしている。実環境でこの上限がどう数えられるかは未確認＝5.5）。
- **完了の印は外れない**（アプリは完了後に印を書き換えない。ルール案でも拒否する）。万一、使っている最中に印が「完了」でなくなったら、その端末は共有データの表示をやめて、状態を確かめ直す。
- 途中で失敗したら（権限・通信など）、印は付かず、理由を表示する。「移行をやり直す」で最初から安全に実行できる。以前の形式は無傷なので、V2 のアプリに戻ることもできる。
- 結果の件数表は画面（データタブ）に出し、`wsMeta/state` にも記録する。
- 「移行せず、空の状態から始める」も選べる（以前の形式のデータは残るが、このアプリには表示されなくなる）。まだ誰も移行を始めていないときだけ選べる。
  押した時点でほかの端末が移行（または初期設定）を始めていた場合は、何も作らず、状態を確かめ直す。
- 以前の形式に ID の無いもの・ID が重複しているもの・Firestore のドキュメント名に使えない ID（`/` を含む、など）があった場合は、止まらずに別の ID を付けて処理し、どう扱ったかを記録する。

**古いアプリとの関係**

- 新しい形式のデータは、古いアプリ（V1・V2）のコードが一切参照しない場所にある。**古いアプリが何を書いても、新しい形式のデータには届かない**（形式の版番号には頼っていない）。
- 移行後に古いアプリで行った変更は、以前の形式の場所に書かれるだけで、Version 3 には反映されない（＝**移行後は、古いアプリを使わない**）。メンバー制のルールでは、古いアプリからは以前の形式の場所にも書けない。
- 形式の版番号（`formatVersion`）は、将来の版との関係にだけ使う（共有データが新しい形式になったら、このアプリは表示と編集を止める）。

### 2.8 後勝ちによって残るリスク・制約（運用で気を付けること）

**後勝ち（同じ項目の同時編集）で起きること** — いずれも、上書きされた側には通知が出ない（画面が最新の内容に変わるだけ）。

| # | 場面 | 起きること |
|---|---|---|
| 1 | 同じ案件の**レイアウト**を 2 人が同時に編集 | レイアウト全体が 1 つの項目なので、後から届いた人の図になり、先の人の変更（椅子を 1 脚足した、など）は消える |
| 2 | 同じ案件の**スタッフ配置**（または実施コンテンツ・その他費用）を 2 人が同時に編集 | それぞれ一覧全体が 1 つの項目。後から届いた人の一覧になる |
| 3 | マスタの同じ行の同じ項目を同時に編集（会場の雛形は雛形全体で 1 項目） | 後から届いたほうが残る |
| 4 | **圏外で編集して戻る**（つながらないまま編集し、あとでつながる） | 圏外のあいだの変更は、つながったときに届く＝「後」になる。その間にほかの人が同じ項目を変えていても、圏外だった人の内容で上書きされる。**間が何日あっても同じ**（ノート PC を閉じて数日後に開いた、圏外のまま画面を閉じて後日開いた、など）。レイアウト・スタッフ配置などは丸ごと 1 項目なので、古い図・古い配置表に戻ることがある。12 時間以上あいた場合は、送信した側の端末に「お知らせ」を出す（2.5）が、**上書きそのものは防がない** |
| 5 | 2 人が、同じ案件の配置図を**同期が済む前に別々の端末で PDF 出力** | 両方とも同じ版番号（例: V1）で出力される。図が違っていれば「同じ版番号で内容の違う PDF」が 2 つできる（版の約束は、1 台の端末・同期済みの状態では守られる） |
| 6 | 削除と編集が同時 | 削除が勝つ。編集した内容は共有に反映されず、案件は控えが端末に残る。削除の取り消し（ごみ箱）は無い |
| 7 | 並び順の同時変更・同時追加 | 同じ番号になったものは ID 順で並ぶ（データは消えない） |

「同時」の幅は、入力が止まってから送るまでの 0.7 秒＋通信時間。圏外のあいだは、戻るまでずっと「同時」扱いになる。
対策の目安: 同じ案件の同じシート（とくにレイアウト・スタッフ配置）を複数人で同時に触らない。圏外で長く編集しない。圏外で編集したら、その日のうちにつないで「保存済み」を確かめる。編集中表示・ロックは未実装（今回の対象外）。

4 を仕組みで防ぐには、「つながっていない間の変更は、端末内の送信待ちに渡さず、つながったときに共有側の状態を確かめてから送る」という作りに変える必要がある（前回の残りの引き取りと同じ扱いを、圏外編集のすべてに広げる）。承認済みの計画（圏外での編集は Firestore 標準の送信待ちに任せる）からの変更になるため、今回は行っていない（**人による判断が必要**。作業ログ参照）。

**その他の制約**

- メンバー制のルールを適用するまでは、**ログインできる Google アカウントなら誰でも共有データを読み書きできる**（現在の本番と同じ状態）。実データを共有に入れるのは、適用後にする。
- プレビュー環境と本番が同じ Firebase プロジェクト・同じチーム名を使っている場合、プレビューでログインして行った操作は、本番と同じ共有データに対する操作になる。
- ログアウトすると、未送信の変更は破棄される（確認あり。確認はほかのタブの分も含めて数える）。確認が出なかった直後にほかのタブで入力した分は、控えに残り、同じアカウントで次にログインしたときに引き取る。
- 1 つのタブがログアウト・アカウントの切り替えをすると、同じブラウザのほかのタブは読み込み直される（端末内キャッシュを消すと、ほかのタブの接続が使えなくなるため。2.5）。
  知らせる仕組み（BroadcastChannel）の無い古いブラウザでは、ほかのタブが読み込み直されず、共有データを確認できない表示になる（手で再読み込みすれば直る）。
  端末内キャッシュを消せない状態が続く場合（ほかのタブが古い版のアプリを開いたまま、など）は、アカウントを切り替えたあとの表示が、毎回 10 秒ほど遅れる（消去を待って時間切れになるため）。
- **前回の残りの引き取りは、ドキュメント単位で判定する**。同じ人が 2 つのタブで同じ案件を編集していて、片方のタブが送る前に突然終了した場合、もう片方の保存が「ほかの人の変更」と同じ扱いになり、終了したタブの変更は自動では反映されないことがある（表示が出て、控えが残る）。
- 前回の残りを送るとき（2.5 の 6）と「共有へコピー」は、サーバーにつながっていて、かつ、この端末の送信待ちが空のときだけ行う。
  送信待ちがなかなか空にならない状態（通信が不安定、など）では、前回の残りは「未送信」のまま画面に出続け、コピーは「送信中の変更が残っている」と表示されて行われない（つながって「保存済み」になれば進む）。
- 「共有へコピー」が途中で失敗した場合、一緒に追加する会場・スタッフなどの一部だけが、先に共有側へ追加されていることがある（案件は最後に作るので、「案件だけあって参照先が無い」状態にはならない）。
  また、通信が途切れて結果を受け取れなかった場合は、「コピーできませんでした」と表示されても、実際にはコピーできていることがある（表示のとおり、案件一覧を確かめてから、やり直す）。
- 前回作成して届かなかったもの（圏外で作成し、送信待ちにも残らなかった場合）は、作り直さない。案件は控えに残るが、マスタ（スタッフ・会場など）は表示だけなので、入力し直す。
- ブラウザの保存領域が使えない環境（プライベートブラウズなど）では、圏外のまま画面を閉じると未送信の変更が失われることがある。
- 1 ドキュメントは 1MB まで（Firestore の上限）。超える案件は保存できず、表示が出て控えが残る。
- 引き取った控えが「ほかの人が変更していた」場合は自動で反映しないので、必要なら控えから手で写す。
- 「（控え）」の案件と「お知らせ」は「この端末だけのデータ」側に残る（ログアウトしても消えない）。共用の端末では、不要になったら削除する。
- 共有データを丸ごと置き換える・全件を一括コピーする機能は無い（1 件ずつコピー）。
- 読み取り回数【概算】: 起動のたびに共有データ全件（案件＋マスタ）を 1 回ずつ読む。数十〜数百件なら無料枠（1 日 5 万回）の範囲と見込む。課金設定には触れていない。

```

置き場所の帯（共有データ／この端末だけのデータ の切り替え。いまどちらを見ているかを常に表示）
上部タブ: 案件｜スタッフ｜会場｜コンテンツ｜パーツ｜データ｜（メンバー）
  案件 ─ 一覧（会場・期間・コンテンツ・売上・費用・利益・警告数／開く・複製・共有へコピー or 端末へコピー・削除）
        │   PC の幅では表（案件名を押しても開く）。スマホ幅（700px 以下）ではカード（カード全体を押して開く。6.3）
        └ 案件詳細（下部シートタブ）
            （JCOS 案件のときだけ）日報の同期の帯 … 「日報を同期」・最終同期・確認が必要なもの（6.2）
            基本情報   … 案件名・会場・期間・既定時間・状態・収支の計算方法（汎用／JCOS 案件）
                          汎用: 固定売上・会場費 ＋ 実施コンテンツ（上限回転数を含む）＋ その他費用
                          JCOS: 請求と支払いの単価 ＋ 実施コンテンツ（予定個数・上限回転数）＋ 追加の請求 ＋ その他実費
            スタッフ配置 … 配置表（スタッフ×日付。クリックで配置／解除）＋ 配置明細（時間・休憩・単価の調整）
            レイアウト  … エディタ（3.3）
            試算     … 汎用: 収支サマリー（計算式つき）＋ 人件費／材料費／備品の内訳
                          JCOS: 粗利・請求・実費 ＋ 内訳 ＋ 材料費の請求と原価 ＋ 予定と実績 ＋ 日別の表（6.1）
  スタッフ／コンテンツ／パーツ … グリッドで直接編集（コンテンツは材料、パーツは椅子の役割と組み合わせ配置の構成も）
  会場 … グリッド ＋ 雛形エディタ（周辺環境のみ）
  データ … サンプル読込（この端末だけのデータへ）、JSON バックアップの保存（表示中の置き場所）・復元（この端末だけのデータへ）、共有データの状態と移行の記録
  メンバー … 名簿（管理者。メンバー制が未適用のあいだは、準備のためログイン中の人に表示）
お知らせ（共有に反映できなかった変更・コピーの結果など。閉じるまで残る）
```

- 複製は、コンテンツ・費用・レイアウトを複製し、**スタッフ配置は引き継がない**（配置は日付に結び付くため。作業ログ D-19）。配置図は V1・未出力から始まる。
- 開いていた案件が、ほかの端末で削除された場合は、一覧に戻って、その旨を表示する。

### 3.1 表計算風グリッド（`components/Grid.tsx`）
行番号・列見出し・罫線・常時編集セル。Enter で下のセル、Shift+Enter で上、Tab で右。合計行は最下段。警告のあるセルは黄色＋⚠（マウスを載せると理由）。
日本語入力の変換を確定する Enter ではセルを移動しない。

数値の欄（`components/NumInput.tsx`。グリッドの数値セル、基本情報の金額欄、図面サイズ）は、PC では表計算と同じく**クリックして打てばその数字に置き換わる**：
- マウス・キーボードでフォーカスすると全選択する。空欄と 0 が同じ意味の欄は、フォーカス中だけ 0 を空欄で見せる（0 の前にカーソルが入り「120」が「1200」になる事故を防ぐ）。
  空欄が「マスタの値を使う」を意味する上書き欄（時給・交通費・参加費）は 0 をそのまま見せる。
- **タッチ（指・ペン）で触れたときは全選択しない**（Version 4）。触れた位置にカーソルが入り、1 桁だけ消して打ち直せる
  （以前はタッチでも全選択していたため、「321 の 1 を消して 0」と打つと、見えない全選択のせいで全桁が消えて 0 になった。Issue #87）。
- 入力欄は `type="text"` ＋ `inputMode="decimal"`（Version 4。スマホでは数字のキーボードが開く）。`type="number"` は、スピンボタン・↑↓ キー・ホイールで値が変わる、
  入力途中の値をブラウザが書き換える、スマホで桁の選択がしにくい、全角の数字を受け取れない、という事故があるため使わない。
- 打たれた文字は `domain/numtext.ts` で数値の表記にそろえる（全角の数字・小数点・マイナスは半角に、桁区切りのカンマ・空白・単位は取り除く）。
  入力途中の文字列はそのまま保つ（「-」から打ち始める、小数点を打つ、先頭の 0、など）。日本語入力の変換中は、確定するまで書き換えない。
- 図面サイズだけは Enter か欄を離れた時に確定する（最小 100cm。1 文字ごとに図面を作り直さない）。何も打たなかった・空欄にした・同じ値だった場合は何も変えない。
- 全選択するのは、クリックや Tab でその欄にフォーカスが入ったときだけ。すでにフォーカスのある欄の中をクリックしたら、その位置にカーソルを置く。
- スマホ（数字だけのキーボード）ではマイナスを打てない。マイナスの値が必要な場合は、PC から入力する（6.4）。

### 3.2 スタッフ配置
- 配置表のセルをクリック → そのスタッフをその日に、案件の既定時間で配置。もう一度クリックで解除。
- 配置前に重複（同案件・他案件）があれば**確認ダイアログで警告し、配置するかどうかを選ぶ**。
- 明細で開始・終了・休憩・時給・交通費を個別に調整。時給・交通費は空欄ならマスタ値（薄い文字で表示）。

### 3.3 レイアウトエディタ（`components/LayoutEditor.tsx`）
- **パーツ配置**モード: 左の表の ［−］［＋］ で定型パーツを増減。「組み合わせ配置」の ［＋配置］ で L字などを1グループとして置く。
- 図面上でドラッグして位置調整（グループは一緒に動く）。吸着 5/10/50cm、矢印キーで微調整（Shift で 50cm）、Delete で削除、Ctrl+Z で元に戻す。
  **Delete キーは、選択枠のとおりに消す**（グループを選んでいればグループごと。作業ログ D-17）。1 台だけ消すのは左パネルの「この 1 台を削除」。
  ドラッグの起点（押した位置を図面座標に直したもの）と、動かす元のレイアウトは、押した瞬間ではなく**最初に動いた時点**で決める。
  押したことで起きる変化（狭い画面で選択欄が伸びて図がずれる／打ちかけの図面サイズが確定する）を取りこぼさず、ドラッグ中のスクロールにも追従する。
- 画面幅 900px 以下では、縦に並べる（図は画面の幅いっぱい）。並び順は **パーツの表 → 図 → 選択中のパーツ → 注記**（Version 4）。
  「選択中のパーツ」と図の警告（重なりなど）は図の下に置く（図の上にあると、パーツを選ぶ・置くたびに欄の高さが変わって、図が上下に動く）。
- **図の近くの「元に戻す」**（Version 4）: 上部のツールバーが画面に見えていない間は、画面の右下（案件の画面では下のシートタブの上）に「元に戻す」を固定で出す。
  図を操作した位置から、上までスクロールせずに戻せる。動きは、ツールバーの「元に戻す」・Ctrl+Z と同じ（同じ履歴を使う）。
- 選択中のパーツ: 表示名の上書き、90°回転、削除（グループのときは「この 1 台を削除」）、グループ解除、グループごと削除。
- 椅子は 2 種類（「椅子（制作席）」＝青、「椅子（その他）」＝灰色）。［＋］［−］で置き分ける（作業ログ D-16）。
- **周辺環境（雛形）**モード: 会場区画・通路・周辺店舗・入口・壁/扉・階段・文字を追加。下のグリッドで名称・位置・サイズ・色・矢印の向きを編集、ドラッグでも移動。図面サイズも変更可。
- タイトル下の注記、**未確認事項**（1行1項目。図の下に黄色い枠で出力）を入力。

### 3.4 配置図の出力（PDF）
- 画面に見えている図（`components/LayoutSvg.tsx`）をそのまま PDF 化（A4・1ページ）。
- タイトル: `{案件名}｜{会場名} イベント配置図 V{版数}`。その下に**会期**（例: `会期 2026/11/13(金)〜11/17(火)`。未入力・不正なら出さない）、注記。右上に作成日。
- ファイル名: `{案件名}_{会場名}_{開始日 YYYYMMDD}_イベント配置図_V{版数}.pdf`（会期が図に出ないときは日付を入れない。作業ログ D-22）。
- **版数**: 新規は V1。PDF を出力するとその版が「出力済み」になる。守ること: **同じ版番号の図は 1 種類だけ**。
  - **エディタでの編集**（会場変更による周辺環境の置き換え・会場雛形の読み直しを含む）は、出力済みの版に手を入れた時点で次の版になる。出力せずに編集している間は上がらない。
  - **エディタの外での変更**（案件名・会場名・会期・パーツマスタの寸法／表示名／区分／椅子の役割など）で図が変わった場合は、**次の版（未出力）として表示**し、何が変わったかをツールバーに示す。
    保存されている版番号は、**次に出力した時点で**変わる（見ただけではデータを書き換えない。作業ログ D-21）。
  - 仕組み: 図は「図のモデル」（`domain/figure.ts`。図に描かれるものだけの一覧）から描く。出力時に、モデルから計算した**指紋**（区分ごと: 案件名・会場名／会期／注記／未確認事項／図面サイズ／周辺環境／パーツ）を、版・日付と一緒に記録する。
    いまの指紋が、その版を出力したときの指紋と違えば「図が変わった」。モデルに無いものは図に出ないので、指紋に入っていないものが図を変えることはない。
    指紋に入れないのは、版番号・作成日・編集用の表示（選択枠・補助グリッド）だけ。単価・保有数・パーツ名・メモなど、図に出ないものを変えても版は上がらない。
  - **元に戻す（Ctrl+Z）では出力の記録を消さない**。出力した時点の状態そのものへ戻り、図も同じならその版に戻る。出力より前の状態まで戻したら次の版になる。
  - 繰り上げ先は「これまでに使ったどの版よりも大きい番号」。変えたものを元に戻して出力時と同じ図になれば、出力済みの版に戻る。
  - 出力済みで図が変わっていない版を出力し直すときは、**その版を最初に出力した日**を作成日に表示する（同じ版の PDF は日付まで同じ）。記録は増えない。
  - **Version 2 までに出力した版**（指紋の記録が無い）は、次の版（未出力）として表示され、次の出力で版が上がる（会期が図に入り、図の見た目自体が変わったため）。
  - パーツマスタの寸法や表示名を直すと、そのパーツを使っている出力済みの全案件が、それぞれ次の出力で版が上がる。
  - 会場マスタの雛形エディタは、会場ごとに「元に戻す」の履歴を分ける。
- 作成日・出力履歴の日付は端末の日付（`localDate`。UTC ではない）。図に描いた日付と、出力の記録の日付は、必ず同じ値にする。PDF の出力処理中は編集を受け付けない。
- 出力の記録は、**出力が終わった時点の最新のレイアウト**に足す（押した時点のレイアウトで丸ごと書き戻さない。出力の処理中に、ほかの端末から届いた変更を消さないため）。記録した指紋といまの図が違っていれば、次の版（未出力）になる。
- グループ名（「L字①」）の位置は四則演算だけで決める（端末によって位置が変わると、指紋＝版の判定が端末ごとに食い違うため）。
- 共有データでは、同期が済む前に 2 台で別々に出力すると、同じ版番号で違う図が出ることがある（2.8 の 5）。

### 3.5 入力チェック（`domain/warnings.ts`）
入力値は拒否・自動修正しない。警告は (a) セルの黄色表示、(b) 案件ヘッダーの「⚠ 警告 n件」一覧、(c) 取り返しにくい操作の前の確認ダイアログ、で知らせる。

| 区分 | 警告する内容 |
|---|---|
| 基本情報 | 案件名なし／会場未選択・**マスタから削除済み**／期間未入力・逆転・**366 日超（試算は 366 日で打ち切り）**／コンテンツ未登録（参考） |
| コンテンツ | 未選択／予定個数 0・マイナス／材料未登録（参考）／上限回転数がマイナス |
| スタッフ配置 | スタッフ未選択・削除済み／期間外の日付／時刻未入力・逆転／休憩が勤務時間以上・**マイナス**／実働6時間超で休憩45分未満・8時間超で60分未満／時給 0 円以下／同案件内の時間重複／他案件との時間重複／誰もいない日（参考） |
| レイアウト | 配置数が保有数を超過／削除済み種別のパーツ／パーツ同士の重なり（5cm 超）／**図面の外にあるパーツ**／**制作席の不足（上限回転数を入力したときだけ）**／雛形未設定（参考） |
| JCOS 案件（Version 4） | 材料原価が 0 円以下／金額がマイナス／日報の同期のあとで会場・会期・会場名（別名）を変えた／同じ会場で会期が重なる案件があり、取り込みを保留している日がある／同期済みの実績のうち、会期が重なる案件があって使っていない日がある（どちらのものか決まっていない＝警告。相手の案件に割り当て済み＝参考）／読み取れずに実績へ入れていない回答がある（同期を止める方式にする前の版が保存した結果にだけ出る。いまの同期は、読み取れない回答があると止まり、同期の欄に内容を表示する）／この案件の実績が無い日に、別の会場名の回答がある（参考）。汎用の試算にだけ関係する確認（スタッフのいない日・時給 0 円・材料の未登録）は出さない |
| 確認ダイアログ | 重複するスタッフの配置、使用中マスタの削除、会場変更時の置き換え、雛形の読み直し・保存、案件削除、サンプル読込・バックアップ復元（「この端末だけのデータ」が空でないとき）、置き場所をまたぐコピー、未送信の変更があるときのログアウト、移行せずに始める |

補足:
- 境界の扱い: 時間の重複は 1 分でも重なれば警告、前の終了＝次の開始は重複としない。休憩は、実働がちょうど 6 時間なら不要で 1 分でも超えたら 45 分、ちょうど 8 時間なら 45 分で足り 1 分でも超えたら 60 分。保有数は「ちょうど」まで可。パーツの重なりは縦横とも 5cm を超えたとき（同じグループ内は対象外）。
- 「中止」の案件は掛け持ちの判定に入れない（相手側としても、その案件自身の警告としても）。
- 実働 0 時間の配置（時刻未入力・逆転）は賃金 0 円だが、交通費は試算に入る。警告文もそのとおりに書く。
- **図面の外にあるパーツ**（作業ログ D-20）: 少しでもはみ出していれば警告（端にぴったり接しているだけなら出ない。向きを反映した寸法で判定）。図面サイズを小さくした・パーツの寸法を大きくした・小さい雛形に置き換えた、などで起きる。パーツは自動では動かさない。
- **制作席の不足**（作業ログ D-16）: 実施コンテンツに「上限回転数」（制作席 1 席が 1 日に受けられる回数）を入力したときだけ判定する。
  必要量 ＝ `Σ（予定個数 ÷ 上限回転数）`（上限回転数を入力したコンテンツだけ。複数のコンテンツは同じ席を使う前提で足す）が、`制作席 × 日数` を**超えた**ら警告（ちょうどなら出ない）。
  制作席が 0 脚のときも警告。空欄・0 なら警告しない。期間が未入力なら判定しない。日ごとの管理はしない（期間合計・全日同じ席数）。
  一部のコンテンツにだけ上限回転数が入っているときは、未入力のコンテンツが確認に入っていないことを「参考」で知らせる。警告文の必要量は小数第 1 位に切り上げて表示する。

## 4. 試算の計算式（`domain/calc.ts`）

日数 `D` ＝ 開始日〜終了日の日数（両端含む）。

| 項目 | 式 |
|---|---|
| 実働時間 (h) | `max(0, 終了 − 開始 − 休憩分) ÷ 60` |
| 人件費（1配置） | `round(実働時間 × 時給) ＋ 交通費`　※時給・交通費は「案件での上書き値、なければマスタ値」 |
| **人件費** | 全配置の合計 |
| 1個あたり材料原価 | `Σ（材料単価 × 1個あたり使用数）` |
| **材料費** | `Σ round(予定個数 ×（1 ＋ 予備率/100）× 1個あたり材料原価)` |
| 参加費売上 | `Σ（予定個数 × 参加費）`　※参加費は「案件での上書き値、なければマスタ値」 |
| **売上 計** | `参加費売上 ＋ 固定売上` |
| **会場費** | `round(固定額 ＋ 日額 × D ＋ 参加費売上 × 歩合/100)` |
| **備品費** | `Σ（レイアウトの配置個数 × 単価 ×（単位が「1日」なら D、「1案件」なら 1））` |
| その他費用 | 入力した費目の合計 |
| **費用 計** | `人件費 ＋ 材料費 ＋ 会場費 ＋ 備品費 ＋ その他費用` |
| **利益** | `売上 計 − 費用 計` |
| 利益率 | `利益 ÷ 売上 計`（売上 0 なら「—」） |
| 制作席（参考） | レイアウト上の「椅子」区分パーツのうち、役割が「制作席」のものの個数（役割が未設定の椅子は制作席として数える） |
| その他の椅子（参考） | 同じく、役割が「その他」のものの個数（席数には数えない） |
| 必要な回転数（参考） | `予定個数の合計 ÷（制作席 × D）`。制作席 1 席が 1 日に何回使われる計算になるか。制作席か D が 0 なら「—」 |

検算例（`domain.test.ts`）: 2日間、100個、参加費500円、予備率10%、材料原価270円、固定売上10万円、会場費 固定1万＋日額2万＋歩合10%、配置 7h×1,200円＋800円 と 5.5h×1,500円＋300円、その他5,000円
→ 売上 150,000／人件費 17,750／材料費 29,700／会場費 55,000／費用計 107,450／利益 42,550。

端数処理: `round` は円未満の四捨五入で、**ちょうど 0.5 は切り上げ**（`util.ts` の `roundYen`）。人件費は配置ごと、材料費はコンテンツ行ごとに丸めてから合計する。
2進小数の誤差で 1 円ずれないよう、掛け算を先に済ませてから割る（賃金＝分×時給÷60、材料費＝個数×(100＋予備率)×原価÷100）。
例: 1個・予備率15%・原価50円 ＝ 57.5 → 58 円、65分・時給1,542円 ＝ 1,670.5 → 1,671 円。
歩合の対象は参加費売上のみ（固定売上は含めない。作業ログ D-04 の仮決定）。

### 6.1 JCOS 案件の収支（`domain/jcos.ts`・`components/JcosView.tsx`）

案件ごとに「収支の計算方法」を選ぶ（基本情報）。**汎用**（4 章の試算。従来どおり）か、**JCOS 案件**。新しい案件・既存の案件・サンプルは汎用のままで、自動では切り替えない。
切り替えても、どちらの入力値も消さない（汎用に戻せば元の試算に戻り、JCOS に戻せば前の条件に戻る）。

JCOS 案件では、**JCOS への請求（売上）**と**こちらの支払い（実費）**を分けて持つ。金額はすべて「編集できる初期値」で、案件ごとに変えられる。

| 項目 | 初期値 | 式 |
|---|---|---|
| 請求：人件費 | 30,000 円／日 | `人件費の請求 × 請求対象日数` |
| 請求：材料費 | 10,000 円／日 | `材料費の請求 × 請求対象日数` |
| 請求：追加（予備費など） | なし | 入力した行の合計（案件によって付く） |
| **請求 計** | | 上の 3 つの合計 |
| 実費：アルバイト代 | 15,000 円／人・日 | `Σ 日（round(その日の人数 × アルバイト代)）` |
| 実費：材料原価 | 220 円／個（暫定） | `Σ 日（round(その日の個数 × 材料原価)）`　※製品の種類（ボトル・バッグ）では分けない |
| 実費：その他 | なし | 「その他実費」に入力した行の合計（明示的に入力したものだけ） |
| **実費 計** | | 上の 3 つの合計 |
| **粗利（管理上）** | | `請求 計 − 実費 計` |
| 粗利率 | | `粗利 ÷ 請求 計`（請求が 0 以下なら出さない） |
| 材料費の超過 | | `max(0, 材料原価の合計 − 材料費の請求の合計)`（自己負担になる額）。日別にも `max(0, その日の材料原価 − その日の材料費の請求)` を出す |

- **請求対象日数とアルバイトの稼働は、別々に数える**。日ごとに「請求する／しない」（既定: する）と「アルバイトの人数」（既定: 1 人）を持つ（`jcos.days`。既定と同じ日は持たない）。
  請求対象日数 ＝ 請求する日の数。アルバイトの稼働 ＝ 人数の合計（人日）。
- **その日の個数**は、実績がある日は実績、無い日は予定を使う。どちらで計算したかを、日ごと・全体で表示する（全体: 予定だけ／一部が実績／全日が実績）。
  - 実績 ＝ 日報の同期の結果（6.2）。同期できない間の代わりに、日別の表で手入力もできる（`actualsManual`）。**同じ日に両方あれば、日報を使う**（手入力は消さずに残し、使っていないことを表示する）。0 個も実績（未入力とは区別する）。
  - 予定 ＝ 実施コンテンツの予定個数の合計を、会期の日数で均等に割ったもの（整数なら、端数は前の日から 1 個ずつ。合計は必ず元の個数と一致する）。
  - 予定だけで計算した粗利も併記する（実績を入れても変わらない）。実績のある日だけの小計も出す。
- **日別の粗利** ＝ その日の請求 − その日のアルバイト代 − その日の材料原価。追加の請求とその他実費は会期全体の項目で、日別には入れない
  （日別の合計 ＋ 追加の請求 − その他実費 ＝ 会期の粗利）。
- 端数: アルバイト代と材料原価は、日ごとに円未満を四捨五入（ちょうど 0.5 は切り上げ）してから合計する（日別の表を足すと、必ず合計と一致する）。
- 表示名は「粗利（管理上）」。自分たちの稼働の原価や税金を含まない管理用の数字で、最終的な利益ではないことを画面に明記する。

**二重計上の防止（汎用の試算の項目との関係）**

| 汎用の項目 | JCOS 案件での扱い |
|---|---|
| 固定売上・参加費売上 | 計算に入れない（請求は、上の表の 3 項目だけ） |
| スタッフ配置の人件費（時給・交通費） | 計算に入れない（支払いはアルバイト代だけ。スタッフ配置の表は、予定の管理用にそのまま使える） |
| 材料マスタによる材料費・予備率 | 計算に入れない（材料原価は 1 個あたりの単価だけで計算する） |
| 会場費 | 計算に入れない |
| 備品費（レイアウト連動） | 計算に入れない。**椅子・テーブルなどを増減・移動しても、粗利は変わらない** |
| その他費用 | 「その他実費」として、そのまま実費に入る（追加のレンタル費・購入費などは、ここに入力したときだけ計上される） |
| 実施コンテンツの予定個数 | 合計を、予定個数として使う |

計算に入れていない項目は、入力値を消さずに残し、試算の画面に「この計算に入れていない項目」として金額つきで表示する（黙って落とさない）。
汎用の案件の計算（`calc.ts` の `estimate`）は変更していない。JCOS の項目を持つ案件でも、`estimate` の結果は変わらない。

### 6.2 日報の同期（`domain/report.ts`・`src/report/`・`components/ReportBar.tsx`）

日報（Google フォームの回答が入るスプレッドシート）の「キットの使用数」を、制作物の実績個数として案件に取り込む。JCOS 案件の見出しの下に「日報を同期」のボタンがあり、押すと次の順に進む。

1. **認証**（`report/googleToken.ts`）: アプリにログイン中の Google アカウントで、読み取り専用の権限（`spreadsheets.readonly`）を求める。
   ふだんのログインには、この権限を付けない（同期のときだけ、Google の確認画面を通る）。得たアクセストークンは、そのタブのメモリにだけ置く（保存しない。約 50 分は使い回す）。
2. **取得**（`report/sheets.ts`）: Google Sheets API を 3 回呼ぶ。タブの一覧（名前と ID だけ）→ 見出し行（1 行目）→ 必要な列だけ（2 行目以降）。
3. **照合と集計**（`domain/report.ts` の `planReportSync`。純関数）→ 結果を案件に書く。

**接続方式を選んだ理由**: 既存の環境（Firebase 認証の Google ログイン）だけで実現でき、新しいサービス・サーバー・秘密鍵・課金が要らない。権限が読み取り専用なので、アプリから日報を書き換えることができない。
公開リンクを使わない（共有を「制限付き」にした日報でも、閲覧権限のあるアカウントなら読める）。
採らなかった案: サービスアカウント＋サーバー側の関数（秘密鍵の発行と保管、ホスティング側の環境変数、サーバーでのメンバー確認が新たに必要）。利用者ごとの同意を無くしたい場合の移行先として残す。

**取得する範囲**: 見出し行と、見出しの名前で特定した「開催日」「会場」「会場（その他の場合）」「イベント名」「キットの使用数」の列だけ。
メールアドレス・入力者・内部用メモ・自由記述・参加者エピソードの列は、要求に含めない（取得しない）。イベント名はテスト回答の判定にだけ使い、保存しない。
列は位置（D・F・G・L）で決め打ちにせず、見出しの名前で確かめる。必要な見出しが無い・同じ見出しが 2 つあるときは、データの列を読まずにエラーにする
（フォームの質問が増減して列がずれた日報から、別の列の数字を取り込まないため）。日付は通し番号、数は数値で受け取る（シートの表示形式に左右されない）。

**照合（会場＋会期）**
- 対象は、開催日が案件の会期内（両端を含む）で、会場名が案件の会場と一致する回答だけ。イベント名は照合に使わない（空欄でも、名前が違っても取り込む）。
- 会場名は、日報の「会場」。それが「その他」（または空欄）のときは「会場（その他の場合）」。
- 一致の判定: 会場マスタの会場名、または会場に登録した「日報での会場名（別名）」と、**全角/半角・空白・英字の大小だけをそろえて**同じであること。部分一致・あいまい一致はしない
  （同じ施設の別の場所——「（ロフト前）」と「（ハーベストコート）」など——を取り違えないため）。
- 会期内で会場名が一致しなかった回答は、取り込まずに、会場名・件数・個数・日付を表示する。「別名として登録して同期」を押すと、その書き方を会場の別名に足して、取り込む（明示的な対応づけ）。
  同じ会期に別の会場のイベントがあるのはふつうなので、一致しない回答があるだけでは確認を求めない。この案件の実績が無い日に別の会場名の回答があるときだけ、確認を求める。
- **テスト回答**（会場名かイベント名に「テスト」「test」を含む）は取り込まない。件数だけ表示する。
  「コンテスト」は、テストの意味ではないので、判定から除く（「フォトコンテスト」という催しの本物の回答を、テスト回答として捨てないため）。英字の test も、単語の一部（contest など）なら数えない。
- **読み取れない回答があるときは、同期の全体を止める**（Issue #88 のオーナー方針「不正値は同期停止」。2026-11-13）。
  一部の回答だけを取り込んだ実績（＝実際より少ない個数）を、確定した実績として扱わないため。止めたときは、案件に何も書かない（前回、正常に取り込んだ結果がそのまま残る）。
  - 読み取れない、とは:
    - 開催日が日付でない・空欄。
    - キットの使用数が、**0 以上 9,999 以下の整数**でない（空欄・文字・単位つき・小数・マイナス・大きすぎる値。0 個とはみなさない）。
      文字で届いた個数は、前後の空白を除いて、数字だけ（全角可）か、3 桁ごとの桁区切り（1,234）だけを受け付ける。
      途中の空白・改行や、区切り方の合わないカンマ（「62 58」「62,58」）は受け付けない（2 つの数をつなげて、6258 個と読んでしまうため）。
      上限（1 件の回答で 9,999 個）は、入力の誤りを止めるためのもの。とくに、個数に「10-20」「11/15」のように入力すると、スプレッドシートがセルを日付に変え、
      日付の通し番号（今年の日付なら 4 万台）が数として届く。それを個数として取り込まない（1990 年以降の日付の通し番号は、すべて上限より大きい）。
    - 会場名が空欄（「その他」で「会場（その他の場合）」が空欄・列が無い場合を含む）、またはスプレッドシートのエラーの値（#N/A など）。
  - **止める回答**: この案件の回答（会場名が一致し、開催日が会期内か、開催日を読み取れない）と、この案件のものかどうかを決められない回答（会場名が空欄で、開催日が会期内か、開催日を読み取れない）に、読み取れない項目が 1 つでもあるとき。
  - **外すだけの回答**（読み取れない項目があっても、この案件の同期は止めない）: この案件のものでないと確実に言える回答。開催日が読み取れて会期の外（会場が何であっても）／会場名が読み取れて、この案件の会場名・別名ではない／
    会場名が一致して開催日が会期内だが、会期が重なる相手の案件が「自分の実績にする」と決めていて、この案件は決めていない日の回答（止まるのは、決めた側の案件の同期）／テスト回答／空行（読む 5 列がすべて空欄）。
  - 止めたときは、回答ごとに「日報の行番号・開催日（読み取れたとき）・読み取れない項目（見出し名）・理由」を表示する（多いときは先頭の 20 件と、残りの件数）。回答に書かれていた文字そのものは、表示も保存もしない。
    行番号は、見出しを 1 行目として数える（日報のスプレッドシートの行番号と同じ）。日報を直してから、もう一度同期する。アプリの中から、その回答を無視して進めることはできない。
  - 止めたときも、日報そのものは読めているので、日報の場所だけは、その端末に覚えておく（最初の同期が止まっても、直したあとで URL を貼り直さずに同期できる）。案件のデータには書かない。
- **同じ会場で会期が重なる案件がほかにある日**（中止の案件は除く）は、どちらの実績か決められないので、取り込まずに保留し、相手の案件名・日付・個数を表示して確認を求める。
  「この案件の実績として取り込む」を押した日（`reportClaims`）だけ取り込む。相手の案件では、その日は「別の案件に割り当て済み」として取り込まない。両方が同じ日を自分の実績と決めた場合は、どちらにも取り込まない。
  保留の日の表示は、保存してある同期の結果より新しい決定に合わせる（決めた直後の同期が失敗した＝「次に同期が成功したときに取り込む」／相手が決めている＝この案件では決めるボタンを出さない／中止の案件＝決めるボタンを出さない）。
- 同じ会場・同じ日の回答が複数あれば合算し、もとの回答の数を表示する。

**反映**
- 1 回の同期で、その案件の「日別の実績」（`reportSync`）を**丸ごと置き換える**（足し込まない）。何度同期しても同じ結果になり（二重計上しない）、日報の修正・削除・追加もそのまま反映される。
- 通信エラー・権限エラー・Sheets API が無効・見出しの不一致（必要な見出しが無い・同じ見出しが 2 つ以上ある）・認証の中断・**読み取れない回答があるとき**は、**案件のデータに何も書かない**（前回の実績が残る）。失敗の内容は、その端末に記録して表示する（次に成功するまで）。
  ほかの端末・ほかのタブで同期が成功して、同期の結果が新しくなったら、その端末に残っている古い失敗は表示しない
  （失敗したときの「最後に成功した同期の日時」を記録しておき、それが変わっていれば古いとみなす。端末どうしの時計のずれに左右されないよう、時刻の前後は比べない）。
- 最終同期日時・読んだ回答の数・取り込んだ回答の数と日数・個数・テスト回答の数・取り込まなかった理由（別の案件に割り当て済みの回答・保留の日・会場名が一致しない回答）を表示する。
- 同期のあとで案件の会場を変えた場合、同期した実績は使わない（別の会場の実績を入れない）。会期を変えた場合は、会期内の日の実績だけを使う。どちらも、同期のやり直しを勧める警告を出す。
- **保存してある実績は、使うたびに、いまの状況と照らす**（`usableReportDays`）。同じ会場名・重なる会期の案件があって、この案件のものと決まっていない日の実績は、保存してあっても使わない。
  同期のあとで、重なる案件が増えた／「この案件の実績にする」の決定を取り消した（そのあとの同期が失敗した場合を含む）／相手の案件も同じ日を自分の実績と決めた、という場合に、
  同じ回答を 2 つの案件で同時に数えないため（PR #89 の Codex レビュー 1 回目の指摘への対応）。どの案件のものかの決め方は、同期のときと同じ関数（`ownerOf`）を使う。
  そのために、1 日分の実績に、合計のもとになった回答の会場名（照合用にそろえた形）を持つ（`ReportDay.keys`）。使っていない日は、同期の帯と警告に、相手の案件名つきで表示する。
  - 取り込んだときの会場名が、いまの会場名・別名に無い日（同期のあとで、会場名や別名を変えた）も、同期し直すまで使わない。
  - 中止の案件は、相手がいる日の実績を自分のものにできない（決定があっても数えない）。進行中の案件は、中止の案件を相手にしない。
  - この決め方で、「同じ会場名・同じ日の回答を、2 つの案件が同時に使うことはない」が、同期の成否や操作の順番によらず成り立つ（単体テストで、無作為の 12,000 手順を確認）。
- 案件を複製しても、実績は引き継がない（複製先は別の会期の案件として使うため）。JCOS の条件（単価・追加の請求）と日報の場所は引き継ぐ。

**保存するもの・しないもの**

| | 保存先 | 内容 |
|---|---|---|
| 同期の結果（`reportSync`） | 案件（共有データなら Firestore） | 同期日時、会場 ID・会期、日別の個数・回答の数・もとになった回答の会場名、件数、取り込まなかった理由（件数と日付）、保留の日、一致しなかった会場名（件数・個数・日付） |
| 日報の場所（`reportSource`） | 案件 | スプレッドシートの ID とタブの ID。一度同期すれば、同じ置き場所のほかの案件・ほかの端末では、入れ直さずに同期できる |
| 日報の場所・最後の失敗 | 端末（localStorage） | この端末で最後に使った場所、案件ごとの最後の失敗の内容（読み取れない回答で止めたときは、日報の行番号・開催日・項目・理由。回答に書かれていた文字は持たない） |
| 保存しない | | アクセストークン、メールアドレス・入力者・メモ・自由記述（そもそも取得しない）、イベント名、個々の回答 |

日報の場所（スプレッドシートの ID）は、リポジトリにもビルドにも入れない。最初の 1 回だけ、アプリで URL を貼る（公開用のリンクは受け付けない）。

**使い始めるのに必要なこと**（アプリの外での設定。6.4 も参照）
1. Firebase のプロジェクト（Google Cloud）で、Google Sheets API を有効にする。
2. 最初の同期のときに、Google の確認画面でスプレッドシートの参照を許可する（Google Cloud の「OAuth 同意画面」が「テスト中」の場合は、同期するアカウントをテストユーザーに追加しておく）。
3. アプリにログインする Google アカウントが、日報を閲覧できること。

### 6.3 スマホ（iPhone の Safari）向けの表示と操作

Issue #87 の実機の報告にもとづく。原因のうち「候補」と書いたものは、実機では未確定（模擬環境で条件を確かめたもの）。

| 報告 | 原因 | 対応 |
|---|---|---|
| 「321」の 1 を消して 0 を打つと 0 になる | 欄に触れるたびに中身を全選択していた（PC の表計算向けの動作）。全選択された状態で削除キーを押すと、全桁が消える。タッチの模擬で再現 | タッチでは全選択しない。入力欄を、数字のキーボードで開く文字入力にした（3.1） |
| 入力時に画面が拡大し、左右が切れる | 入力欄の文字が 13px（iPhone の Safari は、16px 未満の入力欄にフォーカスすると画面を自動で拡大する） | タッチ端末・狭い画面では、入力欄の文字を 16px にした |
| 下のタブが隠れて押せない（その後、回復） | 候補: 画面が拡大されたままだと、画面下に固定したタブが、見えている範囲の外に出る（模擬環境で、1.23 倍の拡大で確認）。恒常的な不具合としては扱わない | 拡大の原因（上の行）を無くした。ページが横にはみ出す画面を無くした。タブを高くし、端末のホームバーのぶん（セーフエリア）の余白を足した |
| 一覧の「開く」が、横スクロールしないと見えない | 表の右端にあった | スマホ幅では、案件をカードで並べる（カード全体を押して開く）。PC の幅の表は、案件名を押しても開く |

- 画面の拡大（ピンチ操作）は禁止していない（見やすさのため。`user-scalable=no` などは使わない）。利用者が自分で拡大した場合、下のタブが見える範囲の外に出るのは変わらない。
- Safari の下部ツールバーが出たり隠れたりする動きとの関係（タブの位置・最初のタップがツールバーの表示に使われる動作）は、模擬環境では確かめられない。実機での確認事項。

### 6.4 制約・残るリスク（Version 4）

- **日報の同期は、実環境では未確認**。確かめたのは、照合と集計（単体テスト）、Sheets API への要求と応答の扱い（応答を差し替えたテスト）、画面の流れ（エミュレータ＋差し替えた応答）、実際の日報の必要列だけを使った照合の試行まで。
  Google の確認画面・Sheets API の有効化・実際の閲覧権限・iPhone の Safari でのポップアップは、実環境でしか確かめられない。
- Google の確認画面では、アプリが未審査のため警告が出る見込み（権限 `spreadsheets.readonly` は、Google の区分で「機密性の高い範囲」）。許可すると、アプリはそのアカウントが閲覧できるすべてのスプレッドシートを読める権限を得る
  （実際に読むのは、指定した日報の必要な列だけ。権限そのものを日報 1 つに絞ることは、この方式ではできない）。
- アクセストークンの有効期限は約 1 時間。切れたあとの同期では、もう一度 Google の画面を通る（iPhone では、ポップアップが止められると同期できない。その場合の案内を表示する）。
- 日報の持ち主が共有を「制限付き」にしたあとは、閲覧権限の無いアカウントでは同期できない（エラーを表示し、実績はそのまま）。
- テスト回答の判定は文字列（「テスト」「test」）による。会場名・イベント名に「テスト」を含む本物の回答（「テストキッチン」という会場、など）は、取り込まれない（除いた件数は表示される）。「コンテスト」だけは、テスト回答の目印にしない。
  逆に、「テスト」と書かれていないテスト回答は、取り込まれる。
- **読み取れない回答が 1 件でもあると、日報を直すまで、その案件の同期は止まる**（安全側に倒した仕様。アプリの中からは、その回答を無視して進められない。その間は、前回の実績のまま。同期していない日には、実績を手入力できる）。
  止まる範囲: 会場名が一致して開催日を読み取れない回答は、その会場のすべての案件の同期を止める。会場名が空欄の回答は、その開催日を会期に含むすべての案件（開催日も読み取れなければ、すべての案件）の同期を止める。
  値として読み取れるが内容が誤っている回答（9,999 個以下の打ち間違い、別の年の日付など）は、検出できない。1 件の回答で 9,999 個を超える実績は、取り込めない（上限は `domain/report.ts` の `MAX_REPORT_COUNT`）。
- 会場名・別名を変えた・外したあとは、変わった名前で取り込んだ日の実績を使わなくなる（警告を出す）。新しい名前での取り込みは、もう一度同期するまで行われない。
- スマホの数字のキーボードではマイナスを打てない（マイナスの金額が必要な場合は PC から）。
- メンバー制のルールを適用するまでは、ログインできる Google アカウントなら誰でも共有データ（日報の場所・同期の結果を含む）を読み書きできる（2.6。Version 3 から変わらない）。
  日報の場所は共有データに入るので、共有データを書き換えられる人は、同期先を別のスプレッドシートに変えることもできる（同期する人のアカウントで読める範囲に限る。読むのは、見出しの名前が合う必要な列だけ）。
  メンバー制を適用すれば、書き換えられるのは名簿の人だけになる。
- 保存されていた Version 4 の項目（JCOS の条件・同期の結果・手入力の実績など）は、読み込むときに形をそろえる（`store/localData.ts` の `hydrateProject`。欠けた項目は補い、扱えない形のものは外す）。
  手で直したバックアップや、ほかの人が書いたデータを読んでも、画面が落ちないようにするため。
- スマホ幅かどうかの判定（案件一覧のカード表示など）は、古い Safari（iOS 13 以前）でも動くようにしてあるが、古い端末での表示そのものは確かめていない。
