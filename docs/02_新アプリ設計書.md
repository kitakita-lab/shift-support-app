# 02. 新アプリ設計書 — KitaKita Lab ワークショップ運営プランナー

版: Version 3 時点（2026-11-12。土台実装は 2026-11-11）。コードと食い違った場合はコード（`src/types.ts`・`src/domain/`・`src/store/`）が正。
Version 3 での変更点（共有データの安全化と、判断 D-16〜D-22 の反映）の経緯・検証結果は `docs/作業ログ.md` の「Version 3」、計画と承認の記録は `docs/03_Version3実装計画.md` を参照。

## 1. 目的と範囲

ワークショップ案件を **会場 × 期間 × 実施コンテンツ** の単位で持ち、次の3つを1か所で計画する。

1. **スタッフ配置** — スタッフリストから人が選んで配置する（自動割当てはしない）
2. **収支試算** — 人件費・材料費・会場費・備品費まで含めた案件ごとの収支
3. **ブースレイアウト** — 会場雛形の上に定型パーツを置き、配置図を PDF で出す。パーツ個数は試算と連動

共通原則:
- **UI は表計算に近い見た目**（グリッド線・行番号・常時編集セル・下部のシートタブ）
- **入力チェックは「禁止せず、警告して選ばせる」**（3.5 参照）

## 2. データモデル

単位: 金額＝円、長さ＝cm、時刻＝`HH:MM`、日付＝`YYYY-MM-DD`。定義は `src/types.ts`。

```
Staff ──┐                        Venue ─── template: Layout（周辺環境のみ）
        │ staffId                  │ venueId
        ▼                          ▼
   Assignment ◀── Project ──▶ ProjectContent ──▶ Content ── Material[]
                     │
                     └── layout: Layout ── env: EnvElement[]   （周辺環境。雛形のコピー）
                                        ├─ items: PlacedItem[] ──▶ PartType
                                        ├─ groups: LayoutGroup[]（L字など）◀── Composite（組み合わせの定義）
                                        └─ version / issued[] / caption / notes
```

### 2.1 マスタ

| 型 | フィールド | 説明 |
|---|---|---|
| `Staff` | name, hourlyRate, transportPerDay, memo | 時給と1勤務日あたり交通費 |
| `Content` | name, price, materials[], memo | 実施コンテンツ。price は参加費（無料なら 0） |
| `Material` | name, unitCost, qtyPerUnit | コンテンツ1個に使う材料の単価と使用数 |
| `PartType` | name, shortName, category, widthCm, depthCm, numbered, unitCost, costUnit, stockQty, seatRole | サイズ固定の定型パーツ。category = table / chair / banner / pop / display / partition / other。`seatRole`（椅子のみ）= work（制作席）/ other（その他）。未設定は制作席として読む |
| `Composite` | name, members[{partTypeId, dx, dy, rot}] | 複数台の組み合わせ（L字など）の定義 |
| `Venue` | name, feeFixed, feePerDay, feeRatePct, memo, template | 会場費の既定値と、レイアウト雛形 |

### 2.2 案件

| 型 | フィールド | 説明 |
|---|---|---|
| `Project` | name, venueId, startDate, endDate, openTime, closeTime, status, memo | 基本情報。status = 計画中 / 確定 / 実施済 / 中止 |
| | contents[], assignments[], otherCosts[] | 実施コンテンツ、スタッフ配置、その他費用 |
| | fixedRevenue, venueFeeFixed, venueFeePerDay, venueFeeRatePct | 固定売上と会場費（会場の既定値をコピーして案件ごとに調整） |
| | layout, updatedAt | ブースレイアウト、最終更新時刻（端末の時計。参考情報で、同期の判定には使わない） |
| `ProjectContent` | contentId, plannedCount, priceOverride, sparePct, maxTurns | 予定個数（期間合計）、参加費の上書き、材料の予備率、上限回転数（制作席 1 席が 1 日に受けられる回数。任意） |
| `Assignment` | staffId, date, startTime, endTime, breakMinutes, rateOverride, transportOverride, memo | 1人×1日の配置。時給・交通費は案件別に上書き可（null ならマスタ値） |

### 2.3 レイアウト

| 型 | フィールド | 説明 |
|---|---|---|
| `Layout` | width, height | 図面全体のサイズ（cm） |
| | env[] | 周辺環境。配列の前にあるものほど奥に描く |
| | items[], groups[] | 配置済みパーツと、組み合わせ配置のグループ |
| | version, issued[] | 現在の版数と、PDF 出力の履歴（版・日付・出力したときの図の内容の指紋 `fp`） |
| | caption, notes | タイトル下の一行注記、未確認事項（1行1項目） |
| `EnvElement` | kind, x, y, w, h, label, sublabel, tone, dir | kind = booth（会場区画）/ passage（通路）/ shop（周辺店舗）/ wall（壁・扉）/ entrance（入口：帯＋矢印＋名前）/ stairs / text |
| `PlacedItem` | partTypeId, x, y, rot(0/90), groupId, label | 左上座標。groupId が同じものは一緒に動く |

設計上の決めごと:
- **雛形はコピーして使う**。案件作成時に会場の `template.env` を案件へ複写する。案件側で周辺環境を直しても雛形は変わらない（「会場雛形として保存」で書き戻せる）。
- **番号は保存しない**。`buildLabels()` が毎回導出する：グループは作成順に ①②…、グループ内のテーブルは `①-1`、グループ外は `表示名＋連番`（例: 商談席1）。増減しても常に連番が保たれる。個別に `label` を入力すればそれが優先で、**その台は連番を使わない**（①-1・受付・①-2。グループ名の副題「横◯台＋縦◯台」は実際の台数のまま）。
- **パーツ個数も保存しない**。`items` を数えるだけ（`countParts()`）。レイアウトと試算が食い違うことがない。

### 2.4 データの置き場所（2 つ。自動では混ざらない）

| 置き場所 | 保存先 | 使える条件 | 入るもの |
|---|---|---|---|
| **この端末だけのデータ** | ブラウザ内（localStorage `kkl_workshop_v1`。V1 から同じキー） | いつでも（未ログイン・Firebase 未設定でも） | 自分で作ったもの。**サンプルの読み込み・バックアップからの復元は、必ずこちらに入る** |
| **共有データ** | Firestore（`teams/{チーム}/…`）。Firestore が正で、端末には「もう 1 つのコピー」を持たない | ログイン中（メンバー制の適用後は、名簿にある人だけ） | チームで共有する案件・マスタ |

- 画面は、いま選んでいる置き場所のデータだけを表示・編集する。どちらを見ているかは、画面上部の色つきの帯（共有＝青／この端末だけ＝黄）に常に出る。
- 置き場所をまたぐのは、案件一覧の **「共有へコピー」／「端末へコピー」** だけ（1 件ずつ・確認つき）。案件が使っている会場・コンテンツ・スタッフ・パーツも、コピー先に無ければ一緒に足す。**コピー先に同じものがあれば上書きしない**（内容が違うものは、その旨を表示する）。コピー元は変わらない。
- 共有データを丸ごと置き換える操作は無い（V2 までの「サンプル読込・復元で共有データが置き換わる」経路を無くした）。
- 「この端末だけのデータ」は変更のたびにすぐ保存する（入力直後に閉じても消えない）。

### 2.5 共有データの同期（`src/store/`）

**Firestore 上の置き場所**（アプリが使う場所は `src/store/paths.ts` だけが組み立てる。一覧は `collections.json`）

| 場所（`teams/{チーム}/` の下） | 内容 |
|---|---|
| `wsStaff`・`wsVenues`・`wsContents`・`wsPartTypes`・`wsComposites` / `{id}` | マスタ。**1 件＝1 ドキュメント**（中身の項目 ＋ 管理用の `order` 並び順・`rev` 書き込みの印・`updatedBy` 最後に書いた人） |
| `wsProjects/{id}` | 案件。1 件＝1 ドキュメント（同上） |
| `wsMeta/state` | 形式の版（`formatVersion: 1`）、使える状態かどうか（`status`）、移行の記録（件数表） |
| `wsBackups/{バックアップ名}__…` | 移行前バックアップ（以前の形式のドキュメントの写し） |
| `members/{メールアドレス（小文字）}` | メンバー名簿（`role: owner / member`） |
| `wsRulesProbe/probe` | 何も置かない。メンバー制のルールでは誰にも許可しない場所。ここを読めたら「ルールが名簿で制限していない」と分かる |
| `workshopData`・`workshopProjects` | V1・V2 の形式。**読むだけ**（移行元）。書き込む処理は無い |
| `appData`・`presence`・`editingStates`・`activityLogs` | 旧アプリ（シフト作成サポート）のデータ。このアプリは読み書きしない |

チーム名は既定で `intention-dev`（環境変数 `VITE_TEAM_ID` で変えられる。プレビューと本番で置き場所を分けたい場合に使う。**現在は設定していない**）。

**同期の規則**（`sharedSession.ts`）

1. **Firestore が正**。画面の内容 ＝ Firestore から届いた内容 ＋ まだ届いた内容に反映されていない自分の変更。
2. **書き込みは 3 種類**: 新しく作る＝「作成」／既にあるものを変える＝「更新」（**自分が変えた最上位の項目だけ**を、入力が止まって 0.7 秒後に送る）／削除。
   - 既にあるものへの変更は必ず「更新」なので、**ほかの端末で削除されたものが復活しない**（Firestore が拒否する）。
   - 送るのは変えた項目だけなので、**別々の項目・別々の行の同時編集は互いを上書きしない**（例: 一方がスタッフ配置、他方がレイアウト）。
3. **入力中の内容は、届いた古い内容で巻き戻さない**（自分が変えた項目だけ手元を優先。触っていない項目は、ほかの人の変更がそのまま見える）。
4. **同じ項目を同時に変えた場合は、後からサーバーに届いたほうが残る**（後勝ち。端末の時計は使わない）。単位は最上位の項目。→ 残るリスクは 2.8。
5. **ログインしただけでは、Firestore に何も書き込まない**。初期設定（「共有データを使い始める」）と移行は、画面のボタンを押したときだけ行う。
6. **送れなかった変更は黙って捨てない**（下の「未送信の変更」「書き込みが拒否されたとき」）。

**未送信の変更**

- 圏外のあいだの変更は、Firestore の端末内キャッシュ（IndexedDB）に送信待ちとして残り、つながると送られる。画面を閉じても残る。ヘッダーに「オフライン（未送信 n 件）」と出る。
- 入力してから送るまでの 0.7 秒のあいだに画面を閉じても消えないよう、変更のたびに **控え**（localStorage `kkl_outbox_v1:…`）へすぐ書く。届いたと確認できたら消す。
- 次に開いたとき、控えが残っていれば引き取る。**送り直す前に、共有側のいまの状態を確かめる**（古い内容で、ほかの人の新しい変更を巻き戻さないため）:

  | 共有側の状態 | 扱い |
  |---|---|
  | 既に届いていた（最後の書き込みの印が一致・内容が同じ） | 何もしない |
  | 誰も触っていない（変更を始めたときの印のまま） | 送り直す（「更新」として） |
  | ほかの人が変更していた | **上書きしない**。表示して、案件は「この端末だけのデータ」に「（控え）」として残す |
  | 削除されていた・保存されていなかった | 復活させない。表示して、案件は控えを残す |

- ログアウトするときに未送信の変更があれば確認を出し、OK なら破棄する（別のアカウントの名前で送られることはない）。

**書き込みが拒否されたとき**（画面上部の「お知らせ」に、閉じるまで表示）

| 原因 | 表示 | データ |
|---|---|---|
| ほかの端末で削除されていた | 「…は、ほかの端末で削除されていたため、変更を共有データに反映できませんでした」 | 復活しない。案件は、編集していた内容を「この端末だけのデータ」に「案件名（控え）」として残す |
| 権限がない（名簿から外された・ルールが変わった） | 「…書き込む権限がないため、反映されませんでした」 | 画面は共有の内容に戻る。案件は控えを残す。登録状況を確かめ直す |
| その他（1 件 1MB の上限超えなど） | 「…保存できませんでした（理由）」 | 同上 |

**共有データの状態**（共有データを選んでいて使えないときは、理由と次の操作を案内する）

| 状態 | 意味 | 画面 |
|---|---|---|
| 確認中 | 登録状況と形式を確認している | 「共有データを確認しています…」 |
| 未登録 | このアカウントは名簿に無い（メールアドレス未確認を含む） | 案内のみ。共有データは読み込まない・端末にも残さない |
| 準備前 | まだ誰も使い始めていない | 管理者: 「共有データを使い始める」ボタン／メンバー: 管理者待ち（用意されると自動で切り替わる） |
| 移行が必要 | 以前の形式のデータがある | 管理者: 「新しい形式へ移行する」「移行せず、空の状態から始める」／メンバー: 管理者待ち |
| 更新が必要 | 共有データが、このアプリより新しい形式 | 表示と編集を止める（古い版で書き換えない） |
| 確認できない | 接続できず、前回の確認結果も無い | 「もう一度確認する」 |
| 使える | — | ヘッダー: 保存済み／同期中…／オフライン（未送信 n 件）／送信待ち（未送信 n 件） |

圏外で開いた場合は、前回の確認結果と端末内キャッシュで表示する（つながったら確かめ直す）。

**アカウントの切り替え**: ログアウト・別アカウントでのログイン・名簿から外されたことが分かった時点で、端末内キャッシュ（閲覧用の控えと送信待ち）を消して接続を作り直す。前のアカウントの共有データは、画面にも端末内にも残さない。

### 2.6 メンバー制（`firestore.v3.rules`・「メンバー」タブ）

- **ルール案**（`firestore.v3.rules`。未デプロイ。`firebase.json` が指す `firestore.rules` は変えていない）:
  - 名簿（`members/{メールアドレス（小文字）}`）にある、メールアドレス確認済みの Google アカウントだけが、そのチームのデータを読み書きできる。
  - 名簿の変更、形式の情報（`wsMeta`）・バックアップ（`wsBackups`）の作成と更新は管理者（`owner`）だけ。バックアップと形式の情報は誰も削除できない。
  - 以前の形式（`workshopData`・`workshopProjects`）は読むだけ。アプリが使う場所だけを名前で許可し、それ以外・2 階層より深い場所はすべて拒否。
  - 旧アプリ（シフト作成サポート）のデータも、名簿の人だけが読み書きできるようになる。
- **アプリは、現在のルールでもメンバー制のルールでも動く**。ログイン時に「自分の登録状況」と「ルールが名簿で制限しているか」を確かめる。
  制限していない（現在のルール）あいだは、帯に「⚠ メンバー制 未適用」と出る（＝ログインできる人は誰でも読み書きできる状態）。
- **「メンバー」タブ**（管理者。未適用のあいだは準備のためログイン中の人に表示）: 追加・役割の変更・削除。メールアドレスは小文字にそろえて登録する。
  管理者が 1 人もいなくなる変更は画面で止める。名簿が空のときは「自分を最初の管理者として登録する」が出る。

**実環境への適用手順（未実施。ご指示をいただいてから）**

1. **事前**: 最初の管理者にする Google アカウントを決める。旧アプリ（シフト作成サポート）を使う人も名簿に入れる必要がある（名簿に無い人は旧アプリのデータも読めなくなる）。
   念のため、Firebase コンソールで Firestore のエクスポート（またはアプリの「バックアップを保存」）を取る。
2. **最初の管理者を登録する**（どちらか）
   - A. Firebase コンソールで `teams/intention-dev/members/{メールアドレス（小文字）}` を作る。項目は `role`（文字列）＝ `owner`、`addedAt`（数値）、`addedBy`（文字列）。
   - B. Version 3 のアプリにそのアカウントでログインし、「メンバー」タブ →「自分を最初の管理者として登録する」。
     （現在のルールのあいだは誰でも名簿を書けるので、登録からルールの切り替えまでを続けて行う。）
3. **ルールを切り替える**: `firestore.v3.rules` の内容を `firestore.rules` に反映してデプロイする（`firebase deploy --only firestore:rules`）。
   切り替え前に、名簿に管理者が 1 人以上いることを確かめる（いないと、切り替え後に誰も名簿を変えられない）。
4. **確認**: 管理者でログインし、「メンバー」タブが「適用中」になっていること。名簿に無いアカウントでは「登録されていません」と出ること。
5. **残りのメンバーを登録**（アプリの「メンバー」タブ）。共有データの初期設定または移行（2.7）は、管理者が行う。
6. **戻し方**: 以前の `firestore.rules` をデプロイし直せば、元の状態（ログインしていれば誰でも可）に戻る。名簿のデータは残る。

**管理者が誰もいなくなった場合の復旧**: 上の 2-A の方法で、Firebase コンソールから管理者を登録し直す（コンソールはルールの制限を受けない）。

### 2.7 以前の形式（V1・V2）からの移行と、古いアプリとの関係

V2 までは、マスタを種別ごとに 1 かたまりで保存していた（`workshopData/{種別}`）。このため、後から保存した端末がかたまりごと上書きし、ほかの人の追加が消えた。Version 3 は 1 件＝1 ドキュメントの新しい場所（`ws…`）を使う。

**移行**（管理者がボタンを押したときだけ。以前の形式のデータは読むだけで、書き換えも削除もしない）

1. 開始を記録する（`wsMeta/state` を `running` に。やり直しのときは同じバックアップ名を使う）。
2. **移行前バックアップ**を取る: 以前の形式のドキュメントの写しを `wsBackups` へ。同じ内容の JSON ファイルを、操作している端末にも保存する（このアプリの「バックアップから復元」で読める形）。
3. 新しい形式で書く。ドキュメント名は元の ID（**やり直しても同じ場所に上書きされるだけで、増えない**）。
4. サーバーから読み直して、**件数と 1 件ずつの内容**を移行元と照合する。
5. 一致して初めて `status: done`（＝移行済みの印）を付ける。**印が付くまで、どの端末も移行先を使わない**。

- 途中で失敗したら（権限・通信など）、印は付かず、理由を表示する。「移行をやり直す」で最初から安全に実行できる。以前の形式は無傷なので、V2 のアプリに戻ることもできる。
- 結果の件数表は画面（データタブ）に出し、`wsMeta/state` にも記録する。
- 「移行せず、空の状態から始める」も選べる（以前の形式のデータは残るが、このアプリには表示されなくなる）。
- 以前の形式に ID の無いもの・ID が重複しているものがあった場合は、止まらずに処理し、どう扱ったかを記録する。

**古いアプリとの関係**

- 新しい形式のデータは、古いアプリ（V1・V2）のコードが一切参照しない場所にある。**古いアプリが何を書いても、新しい形式のデータには届かない**（形式の版番号には頼っていない）。
- 移行後に古いアプリで行った変更は、以前の形式の場所に書かれるだけで、Version 3 には反映されない（＝**移行後は、古いアプリを使わない**）。メンバー制のルールでは、古いアプリからは以前の形式の場所にも書けない。
- 形式の版番号（`formatVersion`）は、将来の版との関係にだけ使う（共有データが新しい形式になったら、このアプリは表示と編集を止める）。

### 2.8 後勝ちによって残るリスク・制約（運用で気を付けること）

**後勝ち（同じ項目の同時編集）で起きること** — いずれも、上書きされた側には通知が出ない（画面が最新の内容に変わるだけ）。

| # | 場面 | 起きること |
|---|---|---|
| 1 | 同じ案件の**レイアウト**を 2 人が同時に編集 | レイアウト全体が 1 つの項目なので、後から届いた人の図になり、先の人の変更（椅子を 1 脚足した、など）は消える |
| 2 | 同じ案件の**スタッフ配置**（または実施コンテンツ・その他費用）を 2 人が同時に編集 | それぞれ一覧全体が 1 つの項目。後から届いた人の一覧になる |
| 3 | マスタの同じ行の同じ項目を同時に編集（会場の雛形は雛形全体で 1 項目） | 後から届いたほうが残る |
| 4 | **圏外で編集して戻る** | 圏外のあいだの変更は、戻ったときに届く＝「後」になる。その間にほかの人が同じ項目を変えていても、圏外だった人の内容で上書きされる |
| 5 | 2 人が、同じ案件の配置図を**同期が済む前に別々の端末で PDF 出力** | 両方とも同じ版番号（例: V1）で出力される。図が違っていれば「同じ版番号で内容の違う PDF」が 2 つできる（版の約束は、1 台の端末・同期済みの状態では守られる） |
| 6 | 削除と編集が同時 | 削除が勝つ。編集した内容は共有に反映されず、案件は控えが端末に残る。削除の取り消し（ごみ箱）は無い |
| 7 | 並び順の同時変更・同時追加 | 同じ番号になったものは ID 順で並ぶ（データは消えない） |

「同時」の幅は、入力が止まってから送るまでの 0.7 秒＋通信時間。圏外のあいだは、戻るまでずっと「同時」扱いになる。
対策の目安: 同じ案件の同じシート（とくにレイアウト・スタッフ配置）を複数人で同時に触らない。圏外で長く編集しない。編集中表示・ロックは未実装（今回の対象外）。

**その他の制約**

- メンバー制のルールを適用するまでは、**ログインできる Google アカウントなら誰でも共有データを読み書きできる**（現在の本番と同じ状態）。実データを共有に入れるのは、適用後にする。
- プレビュー環境と本番が同じ Firebase プロジェクト・同じチーム名を使っている場合、プレビューでログインして行った操作は、本番と同じ共有データに対する操作になる。
- ログアウトすると、未送信の変更は破棄される（確認あり。確認はほかのタブの分も含めて数える）。確認が出なかった直後にほかのタブで入力した分は、控えに残り、同じアカウントで次にログインしたときに引き取る。
- 端末内キャッシュの消去は、同じブラウザのほかのタブが開いていると失敗することがある（次の切り替え時にやり直す）。
- ブラウザの保存領域が使えない環境（プライベートブラウズなど）では、圏外のまま画面を閉じると未送信の変更が失われることがある。
- 1 ドキュメントは 1MB まで（Firestore の上限）。超える案件は保存できず、表示が出て控えが残る。
- 引き取った控えが「ほかの人が変更していた」場合は自動で反映しないので、必要なら控えから手で写す。
- 「（控え）」の案件と「お知らせ」は「この端末だけのデータ」側に残る（ログアウトしても消えない）。共用の端末では、不要になったら削除する。
- 共有データを丸ごと置き換える・全件を一括コピーする機能は無い（1 件ずつコピー）。
- 読み取り回数【概算】: 起動のたびに共有データ全件（案件＋マスタ）を 1 回ずつ読む。数十〜数百件なら無料枠（1 日 5 万回）の範囲と見込む。課金設定には触れていない。

### 3.1 表計算風グリッド（`components/Grid.tsx`）
行番号・列見出し・罫線・常時編集セル。Enter で下のセル、Shift+Enter で上、Tab で右。合計行は最下段。警告のあるセルは黄色＋⚠（マウスを載せると理由）。
日本語入力の変換を確定する Enter ではセルを移動しない。

数値の欄（`components/NumInput.tsx`。グリッドの数値セル、基本情報の金額欄、図面サイズ）は、表計算と同じく**クリックして打てばその数字に置き換わる**：
- フォーカスすると全選択する。空欄と 0 が同じ意味の欄は、フォーカス中だけ 0 を空欄で見せる（0 の前にカーソルが入り「120」が「1200」になる事故を防ぐ）。
  空欄が「マスタの値を使う」を意味する上書き欄（時給・交通費・参加費）は 0 をそのまま見せる。
- スピンボタン（▲▼）は出さない。↑↓ キー・マウスホイールでは値を変えない。
- 入力途中の文字列はそのまま保つ（「-」から打ち始める、小数点を打つ、など）。
- 図面サイズだけは Enter か欄を離れた時に確定する（最小 100cm。1 文字ごとに図面を作り直さない）。何も打たなかった・空欄にした・同じ値だった場合は何も変えない。
- 全選択するのは、クリックや Tab でその欄にフォーカスが入ったときだけ。すでにフォーカスのある欄の中をクリックしたら、その位置にカーソルを置く。

### 3.2 スタッフ配置
- 配置表のセルをクリック → そのスタッフをその日に、案件の既定時間で配置。もう一度クリックで解除。
- 配置前に重複（同案件・他案件）があれば**確認ダイアログで警告し、配置するかどうかを選ぶ**。
- 明細で開始・終了・休憩・時給・交通費を個別に調整。時給・交通費は空欄ならマスタ値（薄い文字で表示）。

### 3.3 レイアウトエディタ（`components/LayoutEditor.tsx`）
- **パーツ配置**モード: 左の表の ［−］［＋］ で定型パーツを増減。「組み合わせ配置」の ［＋配置］ で L字などを1グループとして置く。
- 図面上でドラッグして位置調整（グループは一緒に動く）。吸着 5/10/50cm、矢印キーで微調整（Shift で 50cm）、Delete で削除、Ctrl+Z で元に戻す。
  **Delete キーは、選択枠のとおりに消す**（グループを選んでいればグループごと。作業ログ D-17）。1 台だけ消すのは左パネルの「この 1 台を削除」。
  ドラッグの起点（押した位置を図面座標に直したもの）と、動かす元のレイアウトは、押した瞬間ではなく**最初に動いた時点**で決める。
  押したことで起きる変化（狭い画面で選択欄が伸びて図がずれる／打ちかけの図面サイズが確定する）を取りこぼさず、ドラッグ中のスクロールにも追従する。
- 画面幅 900px 以下では、左の表と図を縦に並べる（図は画面の幅いっぱい）。
- 選択中のパーツ: 表示名の上書き、90°回転、削除（グループのときは「この 1 台を削除」）、グループ解除、グループごと削除。
- 椅子は 2 種類（「椅子（制作席）」＝青、「椅子（その他）」＝灰色）。［＋］［−］で置き分ける（作業ログ D-16）。
- **周辺環境（雛形）**モード: 会場区画・通路・周辺店舗・入口・壁/扉・階段・文字を追加。下のグリッドで名称・位置・サイズ・色・矢印の向きを編集、ドラッグでも移動。図面サイズも変更可。
- タイトル下の注記、**未確認事項**（1行1項目。図の下に黄色い枠で出力）を入力。

### 3.4 配置図の出力（PDF）
- 画面に見えている図（`components/LayoutSvg.tsx`）をそのまま PDF 化（A4・1ページ）。
- タイトル: `{案件名}｜{会場名} イベント配置図 V{版数}`。その下に**会期**（例: `会期 2026/11/13(金)〜11/17(火)`。未入力・不正なら出さない）、注記。右上に作成日。
- ファイル名: `{案件名}_{会場名}_{開始日 YYYYMMDD}_イベント配置図_V{版数}.pdf`（会期が図に出ないときは日付を入れない。作業ログ D-22）。
- **版数**: 新規は V1。PDF を出力するとその版が「出力済み」になる。守ること: **同じ版番号の図は 1 種類だけ**。
  - **エディタでの編集**（会場変更による周辺環境の置き換え・会場雛形の読み直しを含む）は、出力済みの版に手を入れた時点で次の版になる。出力せずに編集している間は上がらない。
  - **エディタの外での変更**（案件名・会場名・会期・パーツマスタの寸法／表示名／区分／椅子の役割など）で図が変わった場合は、**次の版（未出力）として表示**し、何が変わったかをツールバーに示す。
    保存されている版番号は、**次に出力した時点で**変わる（見ただけではデータを書き換えない。作業ログ D-21）。
  - 仕組み: 図は「図のモデル」（`domain/figure.ts`。図に描かれるものだけの一覧）から描く。出力時に、モデルから計算した**指紋**（区分ごと: 案件名・会場名／会期／注記／未確認事項／図面サイズ／周辺環境／パーツ）を、版・日付と一緒に記録する。
    いまの指紋が、その版を出力したときの指紋と違えば「図が変わった」。モデルに無いものは図に出ないので、指紋に入っていないものが図を変えることはない。
    指紋に入れないのは、版番号・作成日・編集用の表示（選択枠・補助グリッド）だけ。単価・保有数・パーツ名・メモなど、図に出ないものを変えても版は上がらない。
  - **元に戻す（Ctrl+Z）では出力の記録を消さない**。出力した時点の状態そのものへ戻り、図も同じならその版に戻る。出力より前の状態まで戻したら次の版になる。
  - 繰り上げ先は「これまでに使ったどの版よりも大きい番号」。変えたものを元に戻して出力時と同じ図になれば、出力済みの版に戻る。
  - 出力済みで図が変わっていない版を出力し直すときは、**その版を最初に出力した日**を作成日に表示する（同じ版の PDF は日付まで同じ）。記録は増えない。
  - **Version 2 までに出力した版**（指紋の記録が無い）は、次の版（未出力）として表示され、次の出力で版が上がる（会期が図に入り、図の見た目自体が変わったため）。
  - パーツマスタの寸法や表示名を直すと、そのパーツを使っている出力済みの全案件が、それぞれ次の出力で版が上がる。
  - 会場マスタの雛形エディタは、会場ごとに「元に戻す」の履歴を分ける。
- 作成日・出力履歴の日付は端末の日付（`localDate`。UTC ではない）。図に描いた日付と、出力の記録の日付は、必ず同じ値にする。PDF の出力処理中は編集を受け付けない。
- 出力の記録は、**出力が終わった時点の最新のレイアウト**に足す（押した時点のレイアウトで丸ごと書き戻さない。出力の処理中に、ほかの端末から届いた変更を消さないため）。記録した指紋といまの図が違っていれば、次の版（未出力）になる。
- グループ名（「L字①」）の位置は四則演算だけで決める（端末によって位置が変わると、指紋＝版の判定が端末ごとに食い違うため）。
- 共有データでは、同期が済む前に 2 台で別々に出力すると、同じ版番号で違う図が出ることがある（2.8 の 5）。

### 3.5 入力チェック（`domain/warnings.ts`）
入力値は拒否・自動修正しない。警告は (a) セルの黄色表示、(b) 案件ヘッダーの「⚠ 警告 n件」一覧、(c) 取り返しにくい操作の前の確認ダイアログ、で知らせる。

| 区分 | 警告する内容 |
|---|---|
| 基本情報 | 案件名なし／会場未選択・**マスタから削除済み**／期間未入力・逆転・**366 日超（試算は 366 日で打ち切り）**／コンテンツ未登録（参考） |
| コンテンツ | 未選択／予定個数 0・マイナス／材料未登録（参考）／上限回転数がマイナス |
| スタッフ配置 | スタッフ未選択・削除済み／期間外の日付／時刻未入力・逆転／休憩が勤務時間以上・**マイナス**／実働6時間超で休憩45分未満・8時間超で60分未満／時給 0 円以下／同案件内の時間重複／他案件との時間重複／誰もいない日（参考） |
| レイアウト | 配置数が保有数を超過／削除済み種別のパーツ／パーツ同士の重なり（5cm 超）／**図面の外にあるパーツ**／**制作席の不足（上限回転数を入力したときだけ）**／雛形未設定（参考） |
| 確認ダイアログ | 重複するスタッフの配置、使用中マスタの削除、会場変更時の置き換え、雛形の読み直し・保存、案件削除、サンプル読込・バックアップ復元（「この端末だけのデータ」が空でないとき）、置き場所をまたぐコピー、未送信の変更があるときのログアウト、移行せずに始める |

補足:
- 境界の扱い: 時間の重複は 1 分でも重なれば警告、前の終了＝次の開始は重複としない。休憩は、実働がちょうど 6 時間なら不要で 1 分でも超えたら 45 分、ちょうど 8 時間なら 45 分で足り 1 分でも超えたら 60 分。保有数は「ちょうど」まで可。パーツの重なりは縦横とも 5cm を超えたとき（同じグループ内は対象外）。
- 「中止」の案件は掛け持ちの判定に入れない（相手側としても、その案件自身の警告としても）。
- 実働 0 時間の配置（時刻未入力・逆転）は賃金 0 円だが、交通費は試算に入る。警告文もそのとおりに書く。
- **図面の外にあるパーツ**（作業ログ D-20）: 少しでもはみ出していれば警告（端にぴったり接しているだけなら出ない。向きを反映した寸法で判定）。図面サイズを小さくした・パーツの寸法を大きくした・小さい雛形に置き換えた、などで起きる。パーツは自動では動かさない。
- **制作席の不足**（作業ログ D-16）: 実施コンテンツに「上限回転数」（制作席 1 席が 1 日に受けられる回数）を入力したときだけ判定する。
  必要量 ＝ `Σ（予定個数 ÷ 上限回転数）`（上限回転数を入力したコンテンツだけ。複数のコンテンツは同じ席を使う前提で足す）が、`制作席 × 日数` を**超えた**ら警告（ちょうどなら出ない）。
  制作席が 0 脚のときも警告。空欄・0 なら警告しない。期間が未入力なら判定しない。日ごとの管理はしない（期間合計・全日同じ席数）。
  一部のコンテンツにだけ上限回転数が入っているときは、未入力のコンテンツが確認に入っていないことを「参考」で知らせる。警告文の必要量は小数第 1 位に切り上げて表示する。

## 4. 試算の計算式（`domain/calc.ts`）

日数 `D` ＝ 開始日〜終了日の日数（両端含む）。

| 項目 | 式 |
|---|---|
| 実働時間 (h) | `max(0, 終了 − 開始 − 休憩分) ÷ 60` |
| 人件費（1配置） | `round(実働時間 × 時給) ＋ 交通費`　※時給・交通費は「案件での上書き値、なければマスタ値」 |
| **人件費** | 全配置の合計 |
| 1個あたり材料原価 | `Σ（材料単価 × 1個あたり使用数）` |
| **材料費** | `Σ round(予定個数 ×（1 ＋ 予備率/100）× 1個あたり材料原価)` |
| 参加費売上 | `Σ（予定個数 × 参加費）`　※参加費は「案件での上書き値、なければマスタ値」 |
| **売上 計** | `参加費売上 ＋ 固定売上` |
| **会場費** | `round(固定額 ＋ 日額 × D ＋ 参加費売上 × 歩合/100)` |
| **備品費** | `Σ（レイアウトの配置個数 × 単価 ×（単位が「1日」なら D、「1案件」なら 1））` |
| その他費用 | 入力した費目の合計 |
| **費用 計** | `人件費 ＋ 材料費 ＋ 会場費 ＋ 備品費 ＋ その他費用` |
| **利益** | `売上 計 − 費用 計` |
| 利益率 | `利益 ÷ 売上 計`（売上 0 なら「—」） |
| 制作席（参考） | レイアウト上の「椅子」区分パーツのうち、役割が「制作席」のものの個数（役割が未設定の椅子は制作席として数える） |
| その他の椅子（参考） | 同じく、役割が「その他」のものの個数（席数には数えない） |
| 必要な回転数（参考） | `予定個数の合計 ÷（制作席 × D）`。制作席 1 席が 1 日に何回使われる計算になるか。制作席か D が 0 なら「—」 |

検算例（`domain.test.ts`）: 2日間、100個、参加費500円、予備率10%、材料原価270円、固定売上10万円、会場費 固定1万＋日額2万＋歩合10%、配置 7h×1,200円＋800円 と 5.5h×1,500円＋300円、その他5,000円
→ 売上 150,000／人件費 17,750／材料費 29,700／会場費 55,000／費用計 107,450／利益 42,550。

端数処理: `round` は円未満の四捨五入で、**ちょうど 0.5 は切り上げ**（`util.ts` の `roundYen`）。人件費は配置ごと、材料費はコンテンツ行ごとに丸めてから合計する。
2進小数の誤差で 1 円ずれないよう、掛け算を先に済ませてから割る（賃金＝分×時給÷60、材料費＝個数×(100＋予備率)×原価÷100）。
例: 1個・予備率15%・原価50円 ＝ 57.5 → 58 円、65分・時給1,542円 ＝ 1,670.5 → 1,671 円。
歩合の対象は参加費売上のみ（固定売上は含めない。作業ログ D-04 の仮決定）。
