## 2. 優先リスクの評価

### 2.1 確かめ方

【事実】この作業環境で **Firebase のエミュレータ（Firestore・認証）が動く**ことを確認した。エミュレータは PC の中だけで動く模擬環境で、実際の Firebase プロジェクトには一切つながらない（`demo-` で始まる架空のプロジェクト ID を使用）。
V2 のコードの接続先だけをエミュレータに向けた作業コピー（リポジトリには入れていない）を使い、ブラウザを 2〜3 個＝別々の端末に見立てて操作した。
V1・V2 で「未検証」としていた同期を、初めて実際に動かしたことになる。**実環境（本物の Firebase）は引き続き未検証**。

### 2.2 D-11 Firestore のアクセス権限 —【評価】最優先。実データを共有に入れる前に必須

【事実】
- 現在のルール（`firestore.rules`）は「ログインしていれば、`teams/intention-dev/` 配下をすべて読み書き可」。名簿による制限は無い。
- エミュレータで、**名簿に無い任意のアカウント**が、案件の一覧取得・案件の読み書き・マスタの書き込み・**旧アプリのデータ（`appData`）の読み取り**まで、すべてできた（付録 A の「現在のルール」）。
- 旧アプリ（現在 `main` から本番公開中）も同じルール・同じ場所を使っている。つまりこの状態は新アプリ固有ではなく、**いまの本番にも当てはまる**。
- 【未確認】実環境に実際にデプロイされているルールが、リポジトリの `firestore.rules` と同じかどうか（確かめたのはリポジトリのファイル）。
- 【未確認】実際の Firebase 側で、ログインできる Google アカウント自体を絞る設定がされているか。されていなければ「Google アカウントを持つ誰でも」になる。

【評価】スタッフの氏名・時給は個人情報にあたる。共有で実データを扱う前に必須。対応は「ルールの変更」が本体で、アプリの修正だけでは防げない（Firebase の接続情報は公開されているアプリに含まれるため、アプリを経由せずに直接読み書きできる）。

【提案】メンバー制
- 名簿: `teams/{チーム}/members/{メールアドレス（小文字）}` に `{ role: 'owner' | 'member' }`。
  メールアドレスをキーにするのは、管理者が相手の内部 ID を調べなくても登録できるため。メールが確認済みのアカウントだけを通す。
- ルール案（付録 A に全文）: 名簿にある人だけがデータを読み書きできる。名簿の変更は `owner` だけ。未登録の人は「自分が登録されているか」だけ確認できる。
- 【事実】このルール案をエミュレータに読み込ませ、**24 項目すべて意図どおり**に動くことを確認した（未登録は全拒否、自分で自分を登録する「なりすまし登録」も拒否、メンバーは名簿を変更不可、メール未確認は拒否、別チームのパスは拒否 など）。
- アプリ側: 未登録のアカウントでログインした場合は「このアカウントはチームに登録されていません」と表示し、同期を止める（この端末だけでは使える）。`owner` には「メンバー」画面（追加・削除）を出す。アプリは**現在のルールでも新しいルールでも動く**ように作る（ルールの切り替えとアプリの公開の順序に依存しない）。

**実環境への適用（Version 3 の実装には含めない。別途ご指示をいただいてから）**
1. 最初の管理者にする Google アカウントを決める。
2. Firebase コンソールで `teams/intention-dev/members/{そのメール}` に `role: "owner"` を 1 件作る。
3. ルールをデプロイする（旧ルールに戻せば元に戻る）。
4. 以後のメンバー追加はアプリの画面から。
旧アプリにも同じ名簿が適用される（名簿に無い人は旧アプリのデータも読めなくなる）。

### 2.3 F-19 サンプル読込による共有データの上書き —【評価】必須。確認ダイアログでは防げない経路がある

【事実】エミュレータで次を再現した（付録 B）。
- (a) ログイン中にサンプルを読み込む → 確認が 1 回出たあと、**共有データが丸ごと置き換わる**。他の人が登録した本番の案件もスタッフも消える（R5）。V2 で確認文を追加した経路だが、メンバーの誰でも 1 回の OK で全員のデータを消せる状態は残っている。
- (b) **ログインせずにサンプルを試し、そのあとログインする → 確認は一度も出ないまま**、
  - サンプルの案件 2 件が共有データに入る（R2）。
  - **共有のスタッフマスタがサンプルで上書きされ、登録してあった本物のスタッフ 2 人が消える**（R4）。ほかの端末の画面からも消える。

【評価】(b) は V2 の報告で見落としていた経路で、V2 の対策（確認文）では防げない。訂正する。「サンプルで試してからログインする」は実機確認でごく自然に起きる手順であり、必須対応。
原因は、アプリが「この端末のデータ」と「共有データ」を同じ入れ物で持ち、ログインした瞬間に自動で混ぜる作りにある。確認を足すのではなく、**混ざらない構造**にする。

【提案】置き場所を 2 つに分ける
- **「この端末だけのデータ」**（これまでどおりブラウザ内に保存。同期しない）と **「共有データ」**（ログイン中。Firestore が正）を別の入れ物にし、**自動では絶対に混ぜない**。
- サンプルは常に「この端末だけのデータ」に入る。ログイン中でもサンプルを開けるが、共有データには触れない。画面上部に、いまどちらを見ているかを常に表示する（色つきの帯）。
- 持ち出しは明示的な操作だけ: 「この案件を共有データへコピー」。案件が参照する会場・コンテンツ・スタッフも一緒にコピーするが、共有側に同じものがあれば上書きしない。
  → サンプルのラソラ案件を実案件の土台として使う場合は、この操作で共有へ移す。
- バックアップからの復元は、まず「この端末だけのデータ」として開く。共有データの全置き換えは、別の明示的な操作（`owner` のみ・件数を表示して確認）にする。
- プレビュー環境と本番で共有データの置き場所そのものを分ける方法（環境ごとにチーム名を変える）も、コード側は対応しておく。実際に分けるには Vercel と Firebase の設定が必要なので、今回は設定しない。

### 2.4 D-12 削除済み案件の復活 —【評価】2 台以上で使い始める前に必須（共同編集の前提）

【事実】エミュレータで再現した（付録 B）。
- R1: 端末 A で案件を削除 → サーバーから消える → **そのとき閉じていた端末 B を開き直しただけで、案件がサーバーに復活**し、A の画面にも戻る。
  作業ログには「長時間オフラインだった端末の再接続で復活することがある」と書いていたが、実際は**「削除の瞬間に開いていなかった端末すべて」**が対象で、ずっと起きやすい。1 人が PC とスマホを使うだけでも起きる。
- R3（同じ原因の別症状）: 端末 B が圏外のあいだに A がスタッフを 1 人追加。B は圏外のまま別のスタッフの時給を修正。B が圏内に戻ると、**A が追加したスタッフが消える**。マスタを種別ごとに 1 かたまりで保存し、後から保存した側が丸ごと勝つため。
  消えたスタッフを登録し直しても内部 ID が変わるので、そのスタッフの配置は全案件で「未選択」になる。

【評価】データが壊れるわけではないが、「消したものが戻る」「足したものが消える」は共同編集の信頼を損なう。**2 台以上で共有を使い始める前に必須**。
原因は F-19 と同じで、端末側に共有データの「もう 1 つのコピー」を持ち、どれが同期済みかをメモリ上でしか覚えていないこと（再読み込みで忘れる）。

【提案】共有時は Firestore を正とし、端末側に別コピーを持たない
- ログイン中の画面の内容は、Firestore から届いたものをそのまま使う。圏外での閲覧・編集は Firestore 標準のオフライン機能（端末内キャッシュと送信待ち）に任せる。
  → 「古いコピーを持つ端末が再アップロードする」ことが構造的に起きなくなる（R1・R2・R4）。
- マスタは「種別ごとに 1 かたまり」から **「1 件＝1 ドキュメント」**に変える（スタッフ 1 人、会場 1 つ…）。別々の行の編集は互いを上書きしない（R3）。
- 削除済みのものへの編集は、書き込みを「既にあるものの更新」として送ることで、復活させない。
  【事実】この前提をエミュレータで確認した: 圏外で送った「更新」は、その間に削除されていると拒否され、削除されたままになる。現行の「丸ごと保存」だと受理されて復活する（付録 B）。
- 同じもの（同じ案件・同じスタッフ）を 2 人が同時に編集した場合は、これまでどおり「後から保存したほうが勝つ」（D-12 の A のまま）。判定は端末の時計ではなくサーバーへの到着順になり、時計のずれの影響を受けなくなる。
- 入力中の内容が、届いた古いデータで巻き戻らないこと（V1 の原則 3）は、編集中のものだけ手元の内容を優先する形で維持する。
- 共有データに「形式の版番号」を持たせ、古いアプリが新しい形式のデータを書き換えないようにする。

**先にテストを書く**: R1〜R4 を自動テスト（エミュレータ＋ブラウザ複数）にし、まず V2 で失敗することを確認してから直す。

### 2.5 Version 3 が入るまでの注意（今すぐ有効）

- **サンプルを読み込んだブラウザでは、ログインしない**（確認なしで共有データに混ざる・マスタを上書きする）。
- 共有（ログイン）に実データを入れるのは、メンバー制の適用後にする。
- すでにプレビューでログインしたことがある場合、共有側の新アプリ用データ（`workshopData`・`workshopProjects`）にサンプルが入っている可能性がある。ログイン後のスタッフ一覧に「スタッフA（サンプル）」があれば該当。
  新アプリは旧アプリのデータ（`appData`）を読み書きしないので、旧データへの影響は無い【事実: コード上、参照箇所が無い】。

## 3. ご判断 D-16〜D-22 の実装方針

### 3.1 D-16（条件付き承認）制作席とそれ以外の椅子の区別 ＋ 回転数の警告

- **椅子を 2 種類のパーツにする**: 「椅子（制作席）」と「椅子（その他）」。図面でも色を変えて見分けられるようにする。
  個々の椅子に切り替えスイッチを付ける方式より、左の表の ［＋］［−］ でそのまま置き分けられ、図を見れば分かる。
  - データ: パーツ種別に `seatRole: 'work' | 'other'`（椅子区分のみ）。既存データの椅子はすべて「制作席」として読む（席数が黙って変わらない）。
- 試算の表示: 「席数」→「**制作席 16／その他の椅子 6**」。
- 回転数の警告（D-16 B）: 実施コンテンツの行に「上限回転数（1 席 1 日あたり）」を追加（任意。空欄なら警告しない）。
  - 必要な回転数 ＝ 予定個数 ÷（制作席 × 日数）を試算に参考表示。
  - 入力がある場合のみ、`Σ（予定個数 ÷ 上限回転数）＞ 制作席 × 日数` で警告（複数コンテンツが同じ席を使う前提）。制作席が 0 の場合も警告。
- 日別管理は対象外（期間合計・全日同じ席数のまま）。
- サンプル: 商談席まわりの 6 脚を「その他」に、残り 16 脚を「制作席」に。ラソラ案件に上限回転数の仮の値を入れる。

### 3.2 D-17（B）グループを選んで Delete → グループごと削除
- Delete／Backspace キーは、選択枠のとおりグループ全体を消す。1 台だけ消すのは左パネルの「削除」ボタン。Ctrl+Z で戻せる。

### 3.3 D-18（B）表示名を上書きしたテーブルは連番を使わない
- ①-2 を「受付」にすると ①-1・受付・①-2。グループ外（商談席 1, 2…）も同じ。グループ名の副題「横◯台＋縦◯台」は実際の台数のまま。

### 3.4 D-19（B）複製ではスタッフ配置を引き継がない
- コンテンツ・費用・レイアウトだけ複製。複製直後は「誰も配置されていない日」の参考表示が日数分出る（期待どおりの動作）。

### 3.5 D-20（B）図面の外にあるパーツを警告
- 「図面の外にパーツがあります（n 個: …）」。少しでもはみ出していれば対象。自動では動かさない。

### 3.6 D-21（A は不採用）図の内容が変わったら、次の出力で版が上がる

【提案】**出力時に「図に描かれる内容の指紋」を記録する方式**
- 図に描かれるものだけを集めた一覧を作る: タイトル（案件名・会場名）、会期（D-22）、注記、未確認事項、図面サイズ、周辺環境、各パーツの位置・寸法・種類・表示ラベル、グループ名。
  単価・保有数・メモなど、図に出ないものは含めない。
- PDF を出力するとき、その一覧から計算した短い値（指紋）を、版・日付と一緒に出力履歴へ記録する。
- 版の状態は「いまの指紋」と「その版を出力したときの指紋」の比較で決める。
  - 一致 → 「V1（出力済み）」。再出力しても V1 のまま。
  - 不一致 → 画面とタイトルは「V2（未出力）」と表示し、**何が変わったか**（例: 案件名、パーツの寸法）も示す。次に出力した時点で V2 として記録する。
- 図は、この一覧から描くように整理する（一覧に無いものは図に出ない＝指紋の取りこぼしが起きない）。

既存の版管理との関係（矛盾しない理由）
- エディタでの編集は、これまでどおり**編集した時点で**次の版になる（D-07 の A のまま）。「元に戻す」の扱いも V2 のまま。
- 今回足すのは、エディタを通らない変更（案件名・会場名・会期・パーツマスタ）を、**出力時に**拾う仕組み。表示だけを先に「V2（未出力）」にし、保存される版番号は出力のときに初めて変える。
  見ただけでデータを書き換えないので、他の端末の編集を上書きしない。
- 「同じ版番号の図は 1 種類だけ」という V2 の約束は、指紋によってエディタの外の変更にも広がる。

この方式の帰結（ご了承いただきたい点。4 章の ★2）
1. パーツマスタの寸法や表示名を直すと、**そのパーツを使っている出力済みの全案件**が「内容が変わった」扱いになり、それぞれ次の出力で版が上がる。
2. V2 までに出力した版には指紋が無い。加えて D-22 で図に会期が入り、図の見た目自体が変わる。このため **V2 までに出力済みの版は、次の出力で版が上がる**。
3. 作成日は毎日変わるため指紋には入れない。そのかわり、出力済みで内容が変わっていない版を再出力するときは、**その版を最初に出力した日**を表示する（同じ版の PDF は日付まで同じになる）。

### 3.7 D-22（B を修正）会期を図面とファイル名の両方に入れる
- 図面: タイトルの下に 1 行追加。例「会期 2026/11/13(金)〜11/17(火)」。会期が未入力なら出さない。
- ファイル名: `ikyu_ラソラ札幌_20261113_イベント配置図_V1.pdf`（開始日）。
- 会期を変えると図が変わるので、3.6 により次の出力で版が上がる。

## 7. データの互換性と移行

- **何も消さない**。この端末のデータ（保存キー `kkl_workshop_v1`）はそのまま「この端末だけのデータ」として読める。

## 10. 追加条件 A〜D と、その対応

承認時に追加された 4 条件を、次のように設計とテストへ反映する。

### A. Firestore Security Rules

| 条件 | 対応 |
|---|---|
| 実際のデータパスとルールの一致 | アプリが使う Firestore の場所を 1 つのファイル（`src/store/paths.ts`）にまとめ、ルール案は**その場所だけを名前で許可**する（「members 以外すべて」ではなく、使う場所の一覧）。一覧どうしが一致していることを自動テストで確かめる。旧アプリ（シフト作成）の 4 か所（`appData`・`presence`・`editingStates`・`activityLogs`）も一覧に含める |
| ネストしたコレクション | アプリは 2 階層目（`teams/{チーム}/{場所}/{ドキュメント}`）しか使わない。それより深い場所は、メンバーでも管理者でも**すべて拒否**されることをテストする |
| メールアドレスの大文字小文字 | 名簿のキーは小文字に統一。ルール側でログイン情報のメールを小文字にして照合し、大文字まじりのキーは作成自体を拒否する。大文字まじりのメールでログインしたメンバーが通ること、名簿に大文字で登録できないことをテストする |
| アカウント変更 | 同じ端末でログアウト→別アカウントでログインしたとき、前のアカウントの共有データが画面にも端末内のキャッシュにも残らないこと、未送信の変更が別アカウントの名前で送られないことをテストする。名簿から外されたメンバーの読み書きが拒否されることもテストする |
| 管理者権限の境界 | メンバーは名簿の変更・自分の昇格・形式情報（`wsMeta`）の変更ができないこと、管理者は別チームに手を出せないこと、名簿の役割に決められた値以外を書けないこと、メールの無いアカウント・メール未確認のアカウントが通らないことをテストする。「最後の管理者が自分を外す」ことはルールでは防げないため、アプリの画面で止め、復旧手順（コンソールから登録）を文書に書く |

ルール案は `firestore.v3.rules` として置く（**`firebase.json` が指す `firestore.rules` は変えない**＝うっかりデプロイされない）。

### B. データ移行

共有データの置き方が変わる（マスタ: 種別ごとのかたまり → 1 件＝1 ドキュメント、案件: 新しい場所へ）。旧形式の場所は**読むだけで、書き換えも削除もしない**。

| 条件 | 対応 |
|---|---|
| 移行前バックアップ | (1) 旧形式のデータそのものを残す。(2) 移行の最初に、旧形式の全データの写しを共有側の別の場所（`wsBackups`）へ保存する。(3) 同じ内容を JSON ファイルとして操作者の端末にも保存する |
| データ件数・内容の照合 | 書き込み後にサーバーから読み直し、種別ごとの件数と、1 件ずつの内容が移行元と一致することを確かめる。結果（件数表）を画面に出し、共有側にも記録する。一致して初めて「移行済み」の印を付ける |
| 再実行時の重複防止 | 移行先のドキュメント名に元データの ID をそのまま使う（同じものは同じ場所に上書きされるだけで、増えない）。「移行済み」の印があれば再実行しない |
| 途中失敗時の復旧 | 「移行済み」の印は照合が通ったあとにだけ付ける。印が無いあいだ、新しいアプリは移行先を使わない。失敗したら理由を表示し、「やり直す」で最初から安全に再実行できる。旧形式は無傷なので、V2 のアプリに戻ることもできる |
| 既存データは削除しない | 旧形式の場所・バックアップとも削除する処理は作らない |

失敗を人為的に起こすテスト（途中で書き込みを拒否させる）を含め、エミュレータで検証する。

### C. 旧クライアントとの互換性

- **形式の版番号には頼らない**。新形式のデータは、古いアプリ（V1・V2）のコードが一切参照しない**新しい場所**（`ws…` で始まる名前）に置く。古いアプリが何をしても、新形式のデータには届かない。
- 確認方法: 実際の V2 のコードをエミュレータにつなぎ、移行後に「サンプル読込」「古いデータを持ったままログイン」「削除」を行っても、新形式のデータが 1 件も変わらないことを確かめる。
- 旧アプリ（シフト作成）が新アプリの場所に触れないことは、コード上の参照箇所の確認と、ルールのテストで確かめる。
- 形式の版番号は、将来の版との関係（新しい形式のデータを、それを知らないアプリが書き換えない）のためだけに使う。

### D. オフライン・競合

| 条件 | テストする内容 |
|---|---|
| 接続切断・再接続 | 圏外で編集 → 圏内に戻ると送られる。圏外のまま再読み込みしても、共有データが見え、未送信の変更が残る |
| 同じ案件の同時編集 | 別々の項目（例: 一方が配置表、他方がレイアウト）なら両方残る。同じ項目なら後から保存したほうが残る |
| 削除後の編集 | 他の端末で削除された案件を編集していた場合、復活しない。編集していた内容は「この端末だけのデータ」に控えとして残し、その旨を表示する |
| 書き込み拒否時の表示 | 権限が無い／削除済み／その他の失敗を、それぞれ画面に表示する（黙って消えない） |

**後勝ちによって残るリスク**は、実装後に作業ログへ明記する（同じ項目の同時編集で先の変更が消える、通知の届かない場面、など）。

## 付録 A. メンバー制のルール案と動作確認

実環境にはデプロイしていない。エミュレータに読み込ませて確認した。

```
rules_version = '2';

service cloud.firestore {
  match /databases/{database}/documents {
    function email() { return request.auth.token.email; }
    function memberPath(teamId) { return /databases/$(database)/documents/teams/$(teamId)/members/$(email()); }
    function isMember(teamId) {
      return request.auth != null
        && request.auth.token.email_verified == true
        && exists(memberPath(teamId));
    }
    function isOwner(teamId) {
      return isMember(teamId) && get(memberPath(teamId)).data.role == 'owner';
    }

    // メンバー名簿: 自分の登録状況は誰でも確認できる。一覧はメンバーのみ。変更は管理者のみ
    match /teams/{teamId}/members/{memberEmail} {
      allow get: if request.auth != null && email() == memberEmail;
      allow read: if isMember(teamId);
      allow write: if isOwner(teamId);
    }

    // チームのデータ（新アプリ・旧アプリとも）
    match /teams/{teamId}/{coll}/{docId} {
      allow read, write: if coll != 'members' && isMember(teamId);
    }

    match /{document=**} {
      allow read, write: if false;
    }
  }
}
```

|---|---|---|---|
| 未登録 | 案件の一覧を読む／1 件読む／書く | **できる** | 拒否 |
| 未登録 | マスタを書く | **できる** | 拒否 |
| 未登録 | 旧アプリのデータを読む | **できる** | 拒否 |
| 未登録 | 自分を名簿に登録する | （名簿なし） | 拒否 |
| 未登録 | 自分の登録状況を確認する | — | できる |
| 未登録 | 他人の登録状況・名簿の一覧を見る | — | 拒否 |
| 未登録 | 別のチーム・チーム外のパスに書く | 拒否 | 拒否 |
| メンバー | 案件・マスタの読み書き、旧アプリのデータを読む、名簿の一覧を読む | — | できる |

## 付録 B. 再現の記録（エミュレータ・V2 のコード）

**R1 削除した案件の復活**
1. A がログインしてサンプルを読み込む → サーバーの案件 2 件
2. B がログイン → B の一覧 2 件。B の端末を閉じる
3. A がデモ案件を削除 → サーバーの案件 1 件
4. B が端末を開き直す → **サーバーの案件 2 件（復活）**。A の一覧にも戻る

**R2 試用データの流入**
1. A が本番の案件を 1 件作成 → サーバー 1 件
2. C が未ログインでサンプルを読み込む → サーバー 1 件のまま
3. C がログイン（確認ダイアログ 0 件）→ **サーバー 3 件（サンプル 2 件が混入）**

**R3 圏外編集による消失**
1. A・B がログイン。サーバーのスタッフ 3 人
2. B が圏外に。A が「新人D」を追加 → サーバー 4 人
3. B が圏外のままスタッフA の時給を 1,250 に変更し、圏内に戻る → **サーバー 3 人（新人D が消失）**、時給は 1,250

**R4 共有マスタの上書き**
1. A が本物のスタッフ 2 人を登録 → サーバー「山田（本物）」「佐藤（本物）」
2. C が未ログインでサンプルを試したあとログイン（確認ダイアログ 0 件）→ **サーバーのスタッフがサンプルの 3 人に置き換わる**。A の画面も同じ

**R5 ログイン中のサンプル読込**
1. A が本番の案件とスタッフ「山田（本物）」を登録 → サーバーにある
2. B がログイン中にサンプルを読み込む（確認ダイアログ 1 件）→ **サーバーの案件はサンプルの 2 件だけ、スタッフはサンプルの 3 人だけになる**（A の本番データは消える）

**設計の前提の確認（削除後の編集）**
- 圏外で「更新」として送る → その間に削除されていると **拒否（not-found）。削除されたまま**
- 圏外で「丸ごと保存」として送る（現行の方式）→ 受理され、**削除した案件が復活**
