### 今回の修正に対する独立レビュー

修正の差分を、経緯を知らない別の AI に読ませて欠陥を探させた。重大な指摘は無かったが、**今回の修正そのものに 6 件の不備**が見つかった。すべて自分でも再現したうえで直し、確認項目（`e2e/verify.mjs`）に加えた。V1 には無かった問題なので、上の 20 件には数えていない。

### 後勝ちによって残るリスク

設計書 2.8 に一覧を置いた。要点:
- **同じ案件の同じシート（レイアウト・スタッフ配置・実施コンテンツ・その他費用）を 2 人が同時に編集すると、後から届いた人の内容になり、先の人の変更は通知なしで消える**（D15 で確認）。別のシートどうしなら両方残る。
- **圏外で編集して戻ると、その間のほかの人の同じ項目の変更を上書きする**（圏外の変更が「後」になるため）。**間が何日あっても同じ**で、レイアウトやスタッフ配置は丸ごと古い内容に戻ることがある。12 時間以上あいた場合は、送信した端末に「お知らせ」を出すが、上書きは防がない（防ぐには作りの変更が必要。下の「人による判断が必要な項目」）。
- 同期が済む前に 2 台で別々に PDF を出力すると、同じ版番号で違う図が出ることがある。
- 削除と編集が重なると削除が勝つ（編集内容は控えに残る）。削除の取り消しは無い。
- 上書きされた側に通知は出ない。編集中表示・ロックは未実装。

### 収支計算の検算（独立した計算経路）

- **台帳方式**（`jcos.test.ts` の `ledger`）: 取引（請求・支払い）を 1 件ずつ書き出して、種類ごとに足す。金額は厳密な分数（BigInt）で持つ。実装は「日別の行を作って足す」作りなので、作りが違う。日付の並べ方・予定の均等割り・実績の選び方も、実装の関数を使わずに書いた。
- 無作為に作った案件 3,000 件（整数の単価）と 1,000 件（小数の単価）で、請求・実費・粗利・個数・材料費の超過が 1 円もずれないこと。日別の合計が会期の合計と合うこと。
- 手計算の受入例 5 件（Issue #88 の例を、材料原価 一律 220 円に直したものを含む）: 1 日・120 個 → 粗利 −1,400 円／1 日・0 個 → 25,000 円／5 日・アルバイト 3 日・310 個 → 86,800 円／5 日・380 個・予備費 20,000・その他実費 8,000 → 53,400 円／単価を変えた場合。
- テストが誤りを見つけられることの確認（実装をわざと 4 通りに壊して、不合格になることを確かめた）: 請求しない日のアルバイト代を 0 にする／材料原価を合計してから丸める／手入力を日報より優先する／超過を日別の合計にする。
- 画面でも、条件から計算した値と照合（`e2e/v4.mjs` の J1〜J7。実装の関数は使わない）。

### 結論

1. **Codex の指摘（P2）は妥当。修正前のコードで再現し、修正後は起きないことを確かめた**（下の「指摘と再現」「テスト」）。
2. 同じタブの中では、同じ案件の同期は 1 つずつになった。案件の画面を閉じて開き直しても「同期中」のままで、結果（成功・失敗）は、開き直した画面に出る。
   それでも重なったとき（同期をやめて、やり直した）は、**最後に始めた同期だけが結果を書く**。最新の同期が失敗していても、先に始めた同期の結果は確定しない。
   古い結果は、画面にも、共有データ（Firestore）にも書かれない。
3. 複数の端末・タブからの同期は、**相手の結果が先に届いていれば、上書きしない**。2 台がほぼ同時に終わった場合は、あとからサーバーに届いたほうが残る
   （どちらか一方の欠けのない結果。守れる範囲の表は、設計書 6.2）。
4. **実機での確認（Google の認証・実際の日報の同期）は、いまの設定のままではできない**ことが分かった（下の「実機での確認を安全に行うための調査」）。
   プレビューのドメインが Firebase の認証で許可されていない（ログインできない）・Google Sheets API が有効になっていない。
   また、プレビューは、本番と同じ Firebase プロジェクト・同じチーム名につながる（分かれていない）。安全に試すための設定と順番を、同じ節にまとめた。こちらでは、設定を変えていない。

### 複数の端末からの同期（調査）

共有データでの書き込みの流れ（`store/sharedSession.ts`。今回は変えていない）:
同期の結果（`reportSync`・`reportSource`）は、案件の最上位の 2 項目として、1 回の「更新」でまとめて送る。画面には、すぐに反映し（手元の変更の重ね合わせ）、0.7 秒後に送る。
同じ項目を 2 台が書いた場合は、あとからサーバーに届いたほうが残る（後勝ち。設計書 2.8）。書く前に相手の内容を確かめる仕組みは、ふだんの編集には無い。

| 場面 | 今回の修正のあと | 根拠 |
|---|---|---|
| A の同期の途中で、B の同期の結果が A に届いた | A は書かない（B の結果が残る）。A に知らせが出る | 単体テスト・R17 |
| A と B が、ほぼ同時に同期を終えた（相手の結果が、まだ届いていない） | どちらも書く。あとからサーバーに届いたほうが残る。残るのは、どちらか一方の欠けのない結果で、2 台の表示は同じ結果にそろう | R18（エミュレータで、2 台の応答を同時に届けた） |
| A が結果を書いた直後（送る前）に圏外になり、あとでつながった | 送信待ちの結果が、あとから届いて上書きする（12 時間以上あいたときは通知。設計書 2.8） | 既存の作り（今回は変えていない。試していない） |
| 同じブラウザの 2 つのタブ（共有データ） | 2 台の端末と同じ（「同期中」の状態は、タブごと）。先に届いていれば、上書きしない | R21 |
| 同じブラウザの 2 つのタブ（この端末だけのデータ） | 守れない。この置き場所は、タブごとに内容を持ち、変更のたびに全体を保存する（同期に限らない、以前からの制約） | 作りから（試していない） |

「ほぼ同時」の幅の目安: 相手が結果を書いてから、送信の待ち（0.7 秒）＋ サーバーへの往復 ＋ こちらへの配信が済むまで。同期 1 回は数秒かかるので、2 人が数秒以内に同じ案件の同期を押した場合に当たりうる。
そのときの影響: 残った結果は、もう一方より先に日報を読んだものかもしれない（その数秒の間に日報が直されていれば、直す前の内容）。
条件（割り当ての決定・別名）が 2 台で違っていた場合は、古いほうの条件で照合した結果が残ることがある。どちらも、もう一度同期すれば直る。
保存してある実績は、使うたびに、いまの決定と照らす（`usableReportDays`）ので、同じ回答を 2 つの案件で数えることは、この場合でも起きない。
仕組みで無くす方法と、入れなかった理由は D-37。

## 判断が必要な点（選択肢と推奨）

土台を動かすために、各項目は **推奨案で仮実装** してある。決定ではないので、別案を選ぶ場合は「変更の手間」を参考に指示してほしい。

### D-01 「材料費（コンテンツとパーツ個数から）」の「パーツ」の解釈
- A: コンテンツを構成する材料（ボトル・花材など）の個数 → 材料費。レイアウトのパーツ（テーブル等）は別枠の「備品費」
- B: レイアウトのパーツ個数（＝席数）から参加可能人数を出し、そこから材料費を逆算
- **推奨: A**（仮実装済み）。材料は「コンテンツ1個あたりの使用数 × 予定個数」、レイアウトのパーツは「個数 × 単価」で備品費に入れ、席数は参考値として試算に表示。
- B を足す場合: 「席数 × 回転数 × 日数 ＝ 上限個数」を出して予定個数と比べる警告を追加（半日程度）。

### D-02 予定個数の持ち方
- A: 期間合計で1つ入力　B: 日別に入力　C: 1日あたり × 日数
- **推奨: A**（仮実装済み）。計画段階では合計で足りる。実績管理まで進めるなら B。

### D-03 売上の持ち方

### D-04 会場費の計算方法

### D-23 JCOS 案件の収支を、どこに・どう足すか（Version 4）
- 事実（オーナーの説明。Issue #87・#88）: JCOS の案件では、「人件費 30,000 円／日」「材料費 10,000 円／日」は JCOS への**請求**（売上）で、支払いではない。支払いは、アルバイト代 15,000 円／稼働日と、材料の原価。椅子やテーブルの数を変えても、通常は利益は変わらない。
- A: 汎用の試算の項目に当てはめる（固定売上に請求額を入れる、など）　B: 案件ごとに「収支の計算方法」を切り替え、JCOS 用の計算を別に持つ　C: 汎用の試算を作り替える
- **採用: B**。汎用の計算式（`calc.ts`）とそのテストは変えない。新しい案件・既存の案件・サンプルは汎用のまま（自動では切り替えない）。切り替えても、どちらの入力値も消さない。
- 理由: A は、請求と支払いの区別・日数の区別・予定と実績の区別を表せない。C は、JCOS 以外の案件に影響する（オーナーの指示: JCOS 以外では従来の計算を維持）。

### D-24 JCOS 案件で、計算に入れるもの・入れないもの（二重計上の防止）
- **オーナーの決定（2026-11-13）**: 請求は 人件費 30,000 円／日・材料費 10,000 円／日・予備費（案件による）。支払いは アルバイト代 15,000 円／稼働日・材料原価 1 個あたり一律 220 円（ボトルとバッグを分けない。暫定値で、案件ごとに変えられる）・その他実費（入力した場合だけ）。配置図のパーツを増減・移動しても、利益は変えない。
- 実装側の設計: JCOS 案件では、汎用の項目のうち **固定売上・参加費売上・スタッフ配置の人件費・材料マスタの材料費・会場費・レイアウト連動の備品費を計算に入れない**。「その他費用」は「その他実費」としてそのまま入れる。予定個数は、実施コンテンツの予定個数の合計を使う。
- 入れていない項目は、入力値を消さず、試算の画面に金額つきで表示する（黙って落とさない。実際に支払うものがあれば「その他実費」に入力してもらう）。
- 別案: 固定売上を「追加の請求」に自動で移す → 採らなかった（サンプルの固定売上 400,000 円は仮の値で、移すと請求が二重になる。何を請求するかは、利用者が明示的に入力する）。

### D-25 請求対象日数・アルバイトの稼働・個数の持ち方
- 日ごとに「請求する／しない」（既定: する）と「アルバイトの人数」（既定: 1 人）を持つ。請求対象日数とアルバイトの稼働（人日）は、別々に数える。
- 個数は、実績がある日は実績、無い日は予定（会期合計の予定個数を日数で均等割り）で計算し、どちらで計算したかを表示する。予定だけで計算した粗利も併記する。
- 別案: アルバイトの稼働を「スタッフ配置」の表から数える → 採らなかった（スタッフ配置には、支払いの無い人も載る。時給の計算と日額の計算が混ざる。配置を変えると粗利が変わる、という見えにくい連動になる）。
- 別案: 予定個数を日ごとに入力する → 入れていない（入力が増える。必要になったら足せる）。
- 日ごとの請求額の例外（半日ぶんだけ請求、など）は、「請求しない」にしたうえで「追加の請求」に行を足すか、「追加の請求」にマイナスの行を足して表す。日ごとの金額の上書きは入れていない。

### D-26 実績個数の手入力と、日報との優先順位

- **同じ日に両方あれば、日報を使う**（オーナーの指示: 日報のキット使用数を、制作物の実績個数として使う）。手入力は消さずに残し、使っていないことを表示する。同期は手入力を書き換えない。
- 別案: 手入力を優先する → 採らなかった（日報が修正されても反映されない日ができる）。別案: 手入力を持たない → 採らなかった（同期の設定が済むまで、実績での粗利を見られない）。

### D-27 日報への接続方式
- **オーナーの条件**: 読み取り専用の安全な認証方式。公開スプレッドシートを前提にしない。既存の環境で実現できる方法を優先。追加課金・公開設定の変更・外部サービスの新規契約が要るなら、実施前に止める。
- A: アプリにログイン中の Google アカウントで、読み取り専用の権限（`spreadsheets.readonly`）を同期のときだけ求め、ブラウザから Google Sheets API を呼ぶ
  B: サービスアカウント＋サーバー側の関数（ホスティングの関数）で読む　C: 選んだファイルだけの権限（`drive.file`）＋ファイル選択の画面　D: 公開リンク＋API キー
- **採用: A**。既存の Firebase 認証（Google）だけで実現でき、新しいサービス・サーバー・秘密鍵・課金が要らない。権限が読み取り専用なので、アプリから日報を書き換えることができない。
- B を採らなかった理由: 秘密鍵の発行と保管、ホスティング側の環境変数の設定、サーバー側でのメンバー確認が新たに必要で、既存の環境だけでは完結しない（利用者ごとの同意が要らない点は B が優れる。必要になったときの移行先）。
- C を採らなかった理由: `drive.file` は、選んだファイルの読み書きの権限で、読み取り専用ではない。ファイル選択の画面の組み込みに、別の API の有効化と API キーが要る。
- D は条件に反する（公開が前提）。
- A の代償: Google の確認画面で、未審査アプリの警告が出る見込み。許可すると、アプリは、そのアカウントが閲覧できるすべてのスプレッドシートを読める権限を得る（実際に読むのは、指定した日報の必要な列だけ）。Google Cloud で Sheets API を有効にする必要がある（無料）。

### D-28 日報の照合と、取り込む範囲

  - 会場名の比較でそろえるのは、全角/半角・空白・英字の大小だけ。別名は会場マスタに登録する（同期の結果から、ワンタップで登録できる）。

### D-34 日報に読み取れない回答があるときの扱い（Version 4 の修正）
- 選択肢: (a) その回答だけ取り込まず、警告を出して続ける（当初の実装）／(b) 同期の全体を止めて、前回の結果を残す。

  理由: 一部の回答だけを取り込んだ個数（実際より少ない）を、確定した実績として粗利に使わないため。
- 実装側で決めたこと（設計）:
  - 止めるのは、「この案件の回答」と「この案件のものかどうかを決められない回答」に読み取れない項目があるとき。この案件のものでないと確実に言える回答（会期の外・別の会場名・テスト回答・空行）は、読み取れない項目があっても外すだけ（指示のとおり）。
  - 会場名が読み取れて一致しない回答は、開催日を読み取れなくても、別の会場の回答として外す（その書き方を別名に登録すれば、この案件の回答になり、そのときは止まる）。
  - 利用者に示すのは、日報の行番号・開催日（読み取れたとき）・項目（見出し名）・理由。回答に書かれていた文字は、表示も保存もしない（必要な列以外を取り込まないのと同じ考え方）。
  - 個数として受け付けるのは、0 以上 **9,999 以下**の整数（以前は 9,999,999 以下）。文字で届いたものは、数字だけか、3 桁ごとの桁区切りだけ。
    上限を下げたのは、日付に変わった個数のセル（通し番号が 4 万台）と、桁の打ち間違いを止めるため。1 件の回答で 9,999 個を超える実績は、いまの運用（1 日 100 個前後）では起きない前提。
    必要になれば、定数（`MAX_REPORT_COUNT`）を変える。値として読み取れるが内容が誤っているもの（上限以下の打ち間違い・別の年の日付）は、検出できない。
  - テスト回答の判定（「テスト」「test」を含む）は、「コンテスト」を除くようにした。それ以外は変えていない（文字列による判定の限界は、設計書 6.4）。
  - 止まったときに、アプリの中から「その回答を除いて進める」手段は入れていない（日報を直すまで止まる。「人による判断が必要な項目（Version 4）」の 7）。

### D-35 同じ案件の同期が重なったときに、どの結果を残すか（Version 4 の修正）
- 選択肢: (a) 届いた順に書く（当初の実装。あとから届いたものが残る）／(b) 重ならないようにするだけ（動いている間は、次を始めない）／
  (c) (b) に加えて、最後に始めた同期だけが書ける・書く前に、同期の結果が、始めたときのままかを確かめる。
- **採用: (c)**（設計）。(b) だけでは、終わらない同期（Google の確認画面を開いたままにした）があると、再読み込みするまで同期できなくなる。
  出口（D-36）を作ると重なりが起きうるので、順番の確認も要る。ほかの端末・タブの同期は、(b) では防げないので、書く前の確認も入れた。
- **最新の同期が失敗したときは、先に始めた同期の結果を書かない**（オーナーの指示）。先の同期は、古い条件（割り当ての決定・別名・日報の場所）で照合していることがある。
  利用者が最後に行った操作の結果（失敗）を見せ、実績は前回のままにするのが、安全側。
- ほかの端末の結果が先に届いていたときは、自分の結果を捨てて、知らせる（黙って上書きしない・黙って捨てない）。
  どちらが新しいかは、端末の時計では決めない（時計のずれに左右されるため。「始めたときの結果のままか」だけを見る）。

### D-36 「同期をやめる」（Version 4 の修正）
- 同期中の状態を、画面を開き直しても残るようにしたので、終わらない同期から抜ける手段が要る（以前は、開き直すと押せる状態に戻った。それが、指摘の不具合の原因でもあった）。
- 同期が 4 秒を超えて続いたら、ボタンと説明を出す（ふつうの同期は数秒で終わるので、毎回は出さない）。押すと、その同期の結果は、あとから届いても使わない。
  通信と Google の確認画面は止めない（止める手段が、認証の側に無い。届いた結果を捨てる）。
- 別案: 一定の時間で自動的にやめる → 採らなかった（Google の確認画面は、利用者が読んで選ぶ時間が要る。時間は決められない）。

### D-37 2 台の端末の同期が、ほぼ同時に終わったときの扱い（Version 4 の修正）
- 選択肢: (a) いまの書き込み（後勝ち）のまま、届いている結果だけを確かめる／(b) 同期の結果を、サーバー側で確かめてから書く（同期日時が変わっていないときだけ書く、トランザクション）。
- **採用: (a)**（設計）。(b) は、共有データの書き込みの作り（変更をまとめて、少し待ってから送る・手元の変更の重ね合わせ・送信待ちの控え）に、別の経路を足すことになる。
  Version 3 で確かめた同期の動作（49 項目）の前提に触れるので、指摘の修正とは分けて判断したい。
- (a) で残るもの: どちらか一方の欠けのない結果が残る／2 台の表示はそろう／もう一度同期すれば直る／同じ回答を 2 つの案件で数えることは起きない（実績を使うたびの確認があるため）。
- (b) にする場合の作業の見込み: `store/remote.ts` に「同期日時が、始めたときのままなら書く」トランザクションを足し、同期の結果だけは、それで書く。
  圏外では書けなくなる（同期そのものに通信が要るので、問題にならない）。書いた内容が購読に届くまでの表示と、送信待ちとの順番を確かめるテストが要る。
- **オーナーの判断（2026-11-14）: 完全な競合の防止は、今回は見送る。既知の制約として扱う**。
  制約の内容: 共有データで、2 台（または 2 つのタブ）が、同じ案件の同期を、ほぼ同時（相手の結果が届く前。目安は 1 秒前後）に終えると、あとからサーバーに届いたほうが残る。
  残るのは、どちらか一方の欠けのない実績。2 台の表示は、同じ結果にそろう。もう一度同期すれば、最新の日報の内容になる。同じ回答を 2 つの案件で数えることは起きない。
  運用: 同じ案件の同期を、複数人が同時に押さない。結果が気になるときは、もう一度同期する。

### D-38 検証用のビルドの見分け方（実機での確認の前提）
- 背景: プレビューは、本番と同じ Firebase プロジェクト・同じチーム名につながる。プレビューだけ `VITE_TEAM_ID` を変えてビルドすると、そのビルドは、本番のチームの場所を読み書きする経路を持たない。
  ただし、環境変数が効いたかどうかは、画面からは分からなかった（確かめるには、配信されたビルドの中身を読む必要があり、そのための取得の機能は、一時的な共有リンクを作る）。
- 採用（設計）: (1) 検証用のビルドは、画面上部の帯に「検証用ビルド（共有データの場所: …）」と常に出す（ログインの前から。通常のビルドには出ない）。
  (2) ビルドのときに、`[kkl] VITE_TEAM_ID=…` を 1 行、記録に出す（配信の記録から、読むだけで確かめられる）。値は秘密ではない（ビルドした JavaScript に、そのまま入る）。
- これは、誤操作を防ぐための分け方と、その見分け方。権限の境界ではない（R25）。権限の境界は、メンバー制のルールの適用か、Firebase プロジェクトの分離で作る。

- 試算の PDF / Excel 出力、案件の実績入力、操作ログは未実装。

Version 4 で分かったもの・変わったもの:
- 数値の欄は、スマホでは数字だけのキーボードが開く（マイナスは打てない）。PC では、これまでどおりクリックして打てば置き換わる。
- 画面幅 900px 以下のレイアウト画面は、並び順が「パーツの表 → 図 → 選択中のパーツ → 注記」になった（選択中のパーツと図の警告が、図の下に移った）。
- JCOS 案件の見出しには「粗利（管理上）」、一覧には「（粗利）」と出る。汎用の案件は、これまでどおり「利益」。
- JCOS 案件では、スタッフ配置の表は収支に入らない（予定の管理用）。アルバイトの人数は、試算の日別の表で入れる。
- 日報の同期は、押した人の Google アカウントの権限で読む。日報を閲覧できないアカウントでは同期できない（実績は変わらない）。
- 「案件の実績入力」は、Version 4 で JCOS 案件に限って入った（日報の同期と、日別の手入力）。試算の PDF / Excel 出力・操作ログは未実装のまま。
- 日報に読み取れない回答（個数が数字でない・空欄、開催日が日付でない、会場名が空欄）があると、その案件の同期は止まり、同期の欄に「日報の何行目の、どの項目か」が出る。日報を直して、もう一度同期する。
- 同期の途中で案件の画面を閉じても、同期は続き、開き直すと「同期中…」のままに見える。4 秒を超えて続くと「同期をやめる」が出る（押すと、その同期の結果は使わない）。
  ほかの端末の同期の結果が先に届いていたときは、自分の同期の結果は使われず、その旨が出る（もう一度同期する）。

Version 3 で分かったもの・変わったもの:

Version 2 の検証で分かったもの（不具合ではないが、知っておくと迷わない）:
